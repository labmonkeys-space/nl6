NVIDIA DCGM simulation

nl6 simulates three NVIDIA GPU servers with eight GPUs each: nvidia_dgx_a100, nvidia_dgx_h100 and nvidia_hgx_h200. The metric vocabulary and the nvidia-smi and dcgmi output are modelled on NVIDIA Data Center GPU Manager (DCGM). The server models, sysObjectID values and the collector OID contract are in GPU simulation.

SNMP​

The OID layout is nl6's own​

1.3.6.1.4.1.5703 is NVIDIA's IANA-registered PEN, so sysObjectID identifies a simulated DGX as an NVIDIA system. Nothing below the PEN is published by NVIDIA. NVIDIA ships no SNMP GPU MIB, and real DCGM exposes a Prometheus /metrics endpoint, not SNMP. Treat the layout below as nl6's contract with its collectors, never as a vendor specification. The arc used to sit under 1.3.6.1.4.1.53246, which is no longer served; see GPU simulation.

No OID below 5703 has an explicit SNMP type. A numeric value is encoded as INTEGER and any other value as OCTET STRING.

Every per-GPU OID is 1.3.6.1.4.1.5703.1.1.1.1.<column>.<gpu>, with <gpu> from 0 to 7.

Value behaviour​

Each GPU holds a pre-generated cycle of 100 points per metric, seeded from a hash of the device IP and the GPU number. The point served depends on the time since the device was created: one point per minute, so a cycle lasts 100 minutes. Reading a column does not move it, so two collectors polling the same OID read the same value, and a walk that reads a dynamic OID without returning it changes nothing. Every metric of every GPU of a device reads the same point at the same instant, so power, temperature, fan speed and both clocks follow the utilization they were derived from. VRAM total is constant.

One SNMP request reads the point once, so every OID in a GET, GETNEXT or GETBULK comes from the same point, even across a minute boundary. Up to v0.38.1 every read returned the next point and each metric had its own cursor, so the value moved per read and the derived metrics drifted apart from utilization.

Standard MIBs​

The profiles also serve system, the IF-MIB interface tables and Host Resources (1.3.6.1.2.1.25). Interface counters come from the same engine as every other device type; see SNMP.

Three Host Resources OIDs are dynamic and come from the device's metrics cycler, not the static resource file. They behave like the per-GPU metrics, including the minute-boundary case, described in Value behaviour.

OIDNameBehaviour
1.3.6.1.2.1.25.3.3.1.2.1hrProcessorLoad.1Cycling CPU percent, moves to the next point once per minute
1.3.6.1.2.1.25.2.3.1.5.1hrStorageSize.1Constant physical memory total from the device profile, never advances
1.3.6.1.2.1.25.2.3.1.6.1hrStorageUsed.1Cycling physical memory used, moves to the next point once per minute

The other Host Resources OIDs, including storage row 2, are static.

REST​

Each profile serves seven GET paths on the device's HTTPS API port (8443 by default). The bodies are static JSON from the *_api.json resource file and do not track the SNMP metric values. There is no per-GPU path such as /api/v1/gpu/devices/{id}. The top-level fields differ between profiles on every path except /api/v1/gpu/devices.
