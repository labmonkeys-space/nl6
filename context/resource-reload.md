# Profile reload is eviction, never mutation (nl6#519)

Moved from CLAUDE.md so the auto-loaded file stays under its size limit. Read this before changing the area it covers.

**Reload is EVICTION, never mutation (nl6#519).** `POST /api/v1/resources/reload` (`resources_api.go`, `ReloadResources` in `resources.go`) drops cache entries so the NEXT device creation reads the profile from disk; optional `resource_file` selects one key (404 if shipped but not cached, 400 if unshipped or not a slug — the two are distinguished by the same stat rule `LoadSpecificResources` uses, because telling a typo "the next creation reads from disk anyway" is false), absent means all, and an explicit `""` is 400. `evictResources` is the THIRD sibling of the nl6#555 seam, under `resourcesCacheMu` for the map operation only, no I/O; the canonical rule in `types.go` names it. **No code path may write into a `*DeviceResources` a device may hold**: a device holds the pointer and serves from indexes built ON that struct, so a device created before a reload serves exactly what it served before and one created after serves the file as it is now. The response says so (`evicted`, `devices_on_old_snapshot` counted per KEY from `DeviceSimulator.resourceFile` under `sm.mu.RLock` — per key and not per evicted pointer, because a device from two generations back is also on a pre-reload snapshot and a pointer comparison under-counts it; `present_on_disk` from a cheap `os.Stat` under the gate; and a `note`), because a caller must not be able to believe existing devices changed. **`sm.deviceResources` is NOT compiled-in — that was wrong in the first draft of this paragraph, the spec and web-api.md.** `loadDefaultResources` reads `resources/asr9k/` from disk, and since nl6#519 it does so THROUGH the cache via `LoadSpecificResources` under key `asr9k.json`, recorded in `sm.defaultResourceKey`; `resolveCreateResources` resolves a create with no `resource_file` through that key, so the whole `-auto-start-ip` fleet's profile is reloadable and a create naming `asr9k.json` and one naming nothing share ONE object (`TestDefaultProfileResolvesThroughTheCache`). Devices with an empty `resourceFile` are counted under that key. The compiled-in `createDefaultResources` constants are the fallback ONLY when no asr9k directory or file exists; that path leaves `defaultResourceKey` empty and stays out of the cache (`TestSynthesisedDefaultStaysOutOfTheCache`). **Trap and syslog catalogs are OUT OF SCOPE by decision**: `trapCatalogsByType` / `syslogCatalogsByType` are loaded at subsystem start and never re-read, and the note and web-api.md say a catalog edit still needs a restart, so that a 200 after a catalog edit is not the nl6#445 accepted-echoed-ignored family; reloading them needs `ApplySizeBudget` re-run under the current MTU plus an atomic map swap (deferred-work.md). **It holds `createBatchGate`, and that is what makes it correct rather than race-free**: every `LoadSpecificResources` call runs inside a gated batch, and `publishResources` keeps the FIRST entry when it re-checks under the write lock, so an evict racing an in-flight load would clear the slot and then watch that load re-publish the OLD file's contents. A reload during a batch is refused 409 with `Retry-After: 5`, fail-fast like nl6#565, and two simultaneous reloads exclude each other the same way. It takes the gate DIRECTLY rather than through `tryEnterCreateBatch` and publishes its OWN token, `sm.resourceReload`, stored after the TryLock and cleared before the Unlock: a reload is not a batch, so `createBatch` stays nil and `create_batch_in_progress` stays false, while `GET /api/v1/status` reports `resource_reload_in_progress` and `createBatchRefusal` tells a colliding create that a RELOAD holds the gate rather than diagnosing a batch with the IP-cursor remedy. The gate is therefore held by two KINDS of holder, and the docs say so. Name validation (`validateResourceFilename`, shared with `LoadSpecificResources`) runs BEFORE the gate, so a malformed name is 400 under a held gate, not 409. No file watcher. Verified by mutation, each watched failing: gate acquisition removed (`TestReloadDuringABatchIs409`, taken INSIDE a real batch through `createBatchStageProbe`); delete replaced by an in-place rewrite, in BOTH the zero-the-struct and the delete-the-key-and-hot-swap-contents forms (`TestReloadedProfileIsServedByTheNextDevice`, through a real `findResponse` on the pre-reload device, in both layouts); `sm.mu.RLock` dropped around the device walk (`TestConcurrentReloadAndDeviceChurn`, 3/3 under `-race`); `resourcesCacheMu` dropped from the evict (`TestConcurrentEvictAndLoad`, mixed layouts, 3/3 under `-race` — and NOT detected by the first shape of that row, which ran one reload per goroutine from a cold cache so every evict found nothing to delete; the row now pre-loads and loops, the nl6#556 spinning-counterpart lesson again); name check moved below the TryLock (`TestReloadInvalidNameIsRefusedBeforeTheGate`); `defer Unlock` replaced by an immediate Unlock, the reload routed through `tryEnterCreateBatch(0)`, and the reload token not published (all three: `TestReloadHoldsTheGateThroughTheEvictAndRefusesACreate`, standing at the end of the evict loop through `reloadWalkProbe`, the seam that exists because every value assertion was green with the gate released right after the TryLock). **What no test here reaches:** the constructor line `resources: deviceResources` inside a completed batch, which needs a listener bind on a device IP; the pin is at `resolveCreateResources`, the resolver both creation paths call.

## The resource cache lock

**`resourcesCache` is guarded by `resourcesCacheMu` (nl6#555).** `LoadSpecificResources` runs on the `net/http` handler goroutine via `resolveCreateResources`, so two concurrent `POST /api/v1/devices` naming different device types were a concurrent map write — which the runtime answers with `throw()`, past any `recover()`, killing the whole simulator rather than one request. **The canonical locking rule lives in the `resourcesCache` comment in `types.go`** — which operations the lock covers, why it is not held across the load, and why an `RWMutex` rather than a `sync.Map` or `sm.mu`. Do not restate it here; the two copies had already diverged once. Two points that are not in that comment: **there are TWO write sites**, because a device type shipped as a directory publishes from `loadSpecificResourcesFromDir` while a legacy single-file type publishes from `LoadSpecificResources` itself, and a test suite that writes only directory fixtures leaves the single-file lock pinned by nothing; and a rejection is still **not** cached, deliberately, so a type stays re-triable once the operator fixes the file (the nl6#538 classification is untouched). Pinned under `-race` by `resources_cache_race_test.go`, which covers both layouts plus a mixed row. Without the lock that test reports a data race **deterministically under `-race`** and a `fatal error: concurrent map writes` on most but not all runs without it — the runtime's concurrent-write detection is best-effort, the race detector is not. CI gates on `make test-race` (`.github/workflows/gates.yml:102`), which is what makes the guard observable there.
