# SNMPv3 USM conformance, and the v1/v3 notification paths



Extracted verbatim from `CLAUDE.md`, which exceeded the 150k-char auto-load limit. This is the long-form record: what the defect was, how it was found, and which mistake it is easy to reintroduce. `CLAUDE.md` carries the short invariants and points here.


**SNMPv3 USM IS RFC 3414 CONFORMANT AND EXTERNALLY VERIFIED (nl6#624), AND THE WAY THAT WAS ESTABLISHED IS THE POINT.** nl6#625 found the stack non-conformant in three ways and, rather than only correcting the seven documents that claimed otherwise, PINNED THE ABSENCE (`snmpv3_usm_unimplemented_test.go`) so the docs could not drift back. That is why this landed as a deliberate edit to a named list of files instead of a surprise; the pins are now presence pins in `snmpv3_usm_conformance_test.go`. **What was wrong:** no HMAC anywhere and 12 ZERO bytes where the digest goes; `AuthProtocol` read by NO production code, so `-snmpv3-auth` changed nothing; the two privacy derivations hardcoding OPPOSITE hashes (`generateDESKey` MD5, `generateAESKey` SHA1, so `md5+des` and `sha1+aes128` accidentally matched RFC 3414 while the other two did not — a first draft of the docs had those rows INVERTED); `getAESKey` deriving from the AUTH password where `Validate`'s own comment promised `PrivPassword`; both IV constructions non-conformant; the engine ID on the wire as the ASCII of its hex SPELLING while localization used the decoded octets; a UNIX EPOCH as `msgAuthoritativeEngineTime`; and inbound messages checked on the USERNAME alone. **They had to be fixed TOGETHER**: a manager localizes its key with the engine ID it RECEIVED, so correcting the digest alone still fails. **THE EXTERNAL CHECK IS THE LOAD-BEARING PART AND IT IS OPT-IN.** `snmpv3_usm_interop_test.go` drives the real dispatcher over a real UDP socket with net-snmp's `snmpget` (6 rows: noAuthNoPriv, authNoPriv MD5/SHA1, authPriv MD5+DES / MD5+AES / SHA1+AES, plus a WRONG-PASSWORD control without which six successful polls prove reachability rather than authentication). `NL6_SNMP_INTEROP=1` gates it because no workflow installs net-snmp and a silent skip asserts nothing — the `testdata/mibs/` lesson. **ITS FIRST RUN FAILED ALL SIX WITH THE PACKAGE GREEN**, which is the whole argument: the fix corrected the engine ID in `wrapScopedPDUInV3Message` and left THREE other emitters (the discovery response, the Report response, `createDiscoveryScopedPDU`) sending the hex spelling and an epoch. A manager DISCOVERS the engine from the first of those and authenticates against another, so it derived a different key and rejected everything, and nothing in the package compared one emitter against another. `TestEveryEmitterAgreesOnTheEngineIdentity` now does — written AFTERWARDS, from a defect only the external stack could see. **Key derivation is verified against RFC 3414 Appendix A.3's PUBLISHED vectors** parsed from a checked-in extract of the RFC (`testdata/rfc/`), not against nl6's output; everything else in the package reads nl6 with nl6's own parser, which is exactly how the original defects survived. **Inbound is verified too**, which is the half an operator is bitten by: `authenticateInbound` answers `usmStatsWrongDigests`, `usmStatsNotInTimeWindows` (the §3.2 150-second window) and `usmStatsUnsupportedSecLevels`, so nl6 CAN now be used to test a collector's wrong-credential handling. Verification is conditional on the REQUEST's auth flag, not on the device's configuration — USM authenticates a message at the level that message declares, and rejecting an unauthenticated request from a configured-auth device would be nl6 inventing a policy the RFC does not state. **The skipped time window's stated justification did not survive contact**: it cited operators with "intentionally skewed clocks", which was an artefact of the defect beside it, since a UNIX epoch really is at the mercy of wall-clock skew while seconds-since-boot is a value the manager learns from us. **`assembleV3`, the single test builder, now SIGNS**, so the whole v3 test surface became a round-trip proof of the digest rather than a proof that nothing checked it, and it sets the AUTH flag only when the server actually authenticates. **THE REVIEW FOUND MORE THAN THE IMPLEMENTATION DID, AND TWO OF ITS FINDINGS WERE DEFECTS THIS CHANGE ITSELF SHIPPED.** (1) `substituteAuthParams` located the digest field by SEARCHING for `04 0C` plus twelve zeros — byte-for-byte how an OCTET STRING value of twelve zero octets encodes — so a device serving such a value made the match ambiguous and the whole response fail to assemble: an authNoPriv GET of that OID returned NOTHING, with no log line, reachable from an ordinary operator resource file. The in-code comment defending the search argued a tracked offset was riskier; it had the trade backwards, since only the search is defeatable by data nl6 does not control. Both are avoided by `locateAuthParams`, which WALKS THE MESSAGE STRUCTURE. (2) The AES IV and `msgAuthoritativeEngineTime` were TWO SEPARATE CLOCK READS, so a response assembled across a second boundary shipped an IV built from T while advertising T+1 — the nl6#625 defect class reintroduced in a form far harder to see. `wrapScopedPDUInV3Message` now takes ONE sample and passes it to both (`encryptScopedPDUAt`), and so do the test helpers, where the same mistake is just as easy to write. **THE VERIFICATION HALF MATTERED MORE THAN THE FIX**: advertising a time 1000 seconds from the IV's left the whole package GREEN, because `decodeV3ResponsePossiblyEncrypted` decrypted with the server's own live clock, so both sides sampled independently and agreed by accident. It now decrypts with the values the RESPONSE CARRIES, which turns every authPriv row in the package into an assertion of the property; `snmpv3_usm_wire_test.go` additionally reconstructs both IVs with the STANDARD LIBRARY from the wire alone, since an IV that is wrong but SYMMETRIC passes every round trip through nl6's own code. **`sha1+des` was exercised by NOTHING** while the docs called it conformant: the localized privacy key is 16 octets under MD5 and 20 under SHA1 and both consumers slice it at FIXED indices, so writing the pre-IV as "the last 8 octets" is right for MD5 and wrong for SHA1 — mutation-verified, md5 passes and sha1 fails. Every privacy check now runs under both hashes and the interop set is all seven rows. **THE INTEROP CHECK IS NOW A CI GATE** (`make test-interop`; the workflow installs net-snmp), because leaving the one test with detection power opt-in would retire it. **Also from review:** an unknown USER was a silent drop while a wrong DIGEST got a Report, so a collector could not tell it from an unreachable device — now `usmStatsUnknownUserNames`; the `usmStatsNotInTimeWindows` Report is SIGNED so a manager can trust the `(boots, time)` it carries and resynchronise, while `usmStatsWrongDigests` deliberately is not, the peer's key disagreeing with ours by definition; PRIV-without-AUTH is refused as an unsupported security level rather than decrypting on unverified boots/time; `withinTimeWindow` range-checks BEFORE negating, since negating `math.MinInt` is a no-op and let an extreme declared time pass the 150-second window; privacy now REQUIRES an auth protocol at `Validate` (it used to be accepted and then fail on every request with "no localized key is available"); and `usmPasswordToKey` caches Ku across devices, which is the reason the RFC's two steps were split in the first place — held per device, a 30,000-device fleet spent ~2 CPU-minutes on an intermediate identical for every one of them, inline on the shared UDP handler. **nl6#624's ONE EXPLICIT PROOF OBLIGATION CANNOT BE MET AND IS RECORDED RATHER THAN DODGED:** it asked for proof the noAuthNoPriv path stayed byte-identical, on the assumption the fix touched only authenticated paths. THREE defects are in the envelope every level shares (engine ID as hex spelling, engine time as a UNIX epoch, twelve zero octets where §6.3.1 wants zero LENGTH), so byte-identity would mean keeping them. `TestNoAuthNoPrivWireDeltaIsRecorded` pins exactly the three fields that moved, and any FURTHER drift fails there. **STILL NOT IMPLEMENTED:** SNMPv3 INFORM (nl6#98 shipped v3 TRAPS on this foundation — see the SNMPv3 notifications paragraph below — and left INFORM out because it is receiver-authoritative), and RFC 7860's SHA-2 protocols / AES-192/256. **THE THREE SEAMS nl6#98's ENCODER NEEDS ARE ALREADY LIFTED, WITH NO SECOND CALLER AND NO BEHAVIOUR CHANGE:** `wrapInScopedPDU` (the RFC 3412 §6 ScopedPDU envelope, PDU-agnostic so it can carry a `0xA7`, and now the ONLY copy — `createDiscoveryScopedPDU` was migrated onto it, which is the pair that drifted in nl6#624), `wrapScopedPDUInV3MessageWith(scopedPDU, msgID, msgFlags, userName)` (the v3 envelope with its three response-shaped inputs supplied directly, `wrapScopedPDUInV3Message` now a thin adapter over it), and `encodeNotificationPDU` (the notification PDU body, identical under v2c and v3, with the community envelope left behind in `encodeV2cNotification` — `encodeV2cNotificationFast` keeps its own PDU region by decision). All four affected paths are pinned byte-for-byte by digests MEASURED AT THE BASELINE COMMIT IN A WORKTREE (`trap_pdu_extraction_test.go`, all four in `loadBearingGuards`), and `usmPrivSaltRead` joins `FlowExporter.writeOverride` and `createBatchStageProbe` as a test seam — `crypto/rand.Read` in production, pinned by `TestPrivSaltSeamIsInitialisedFromCryptoRand`, which asserts the DECLARATION because the behavioural test cannot: pointing the seam at ONE seeded math/rand generator left the whole package green — every digest overwrites the default via `pinPrivSalt` first, and 64 distinct non-zero draws are a property of any non-repeating stream, not of a CSPRNG — while the DES IV became predictable. The seam is needed because an authPriv message is random by construction and otherwise cannot be compared across commits at all. **TWO ENGINE-IDENTITY LIMITS ARE DOCUMENTED, NOT FIXED:** `snmpEngineID` is fleet-wide while `(boots, time)` is per device, and `engineBoots` is always 1 and not persisted, so a restart rewinds engine time under unchanged boots where RFC 3414 §2.2.3 would increment boots.

**SNMPv1 Trap-PDU (nl6#97).** `-trap-snmp-version v1|v2c` (default v2c) switches the fleet to the RFC 1157 Trap-PDU (tag `0xA4`, message `version` 0). **NO CATALOG SCHEMA CHANGE, and that was measured before it was designed:** nl6#97 proposed per-entry enterprise/generic/specific fields, but of the 23 shipped entries 5 are standard traps and 18 are enterprise-specific, and RFC 3584 §3.2 derives every field of the v1 identity from the `snmpTrapOID` they already carry. Hand-writing three fields on 23 entries would be 23 chances to disagree with the OID beside them. **A DECLARED `snmpTrapEnterprise` IS NOT AN OVERRIDE** and this is the one place the mapping surprises: RFC 3584 honours it ONLY for a standard trap, so across the shipped corpus it is used by the v1 path in ZERO cases (the 5 standard entries declare none; every vendor entry derives). An earlier draft of the spec had this backwards; READING the RFC rather than recalling it is what caught it, which is also why `snmpTrapsOID` (`1.3.6.1.6.3.1.1.5`) is re-derived from the corpus by `TestSnmpTrapsOIDIsTheStandardTrapPrefix` rather than trusted as a constant. **A v1 PDU carries NONE of the three varbinds v2c prepends** (`sysUpTime.0` → `time-stamp`, `snmpTrapOID.0` → the identity, `snmpTrapEnterprise.0` → `enterprise`); emitting them would produce a trap no real agent sends. **`SNMPv1Encoder` is PER DEVICE** where `SNMPv2cEncoder` is shared, because `agent-addr` is the originator's own IP: that is per-device state, not a per-call parameter, and modelling it as state left `TrapEncoder` untouched on the path this change had to leave byte-identical. **NO v1 INFORM** (RFC 1157 defines none): refused at startup for the seed flags and at attach for a REST device. `EncodeInform`/`ParseAck` are the backstop, not the diagnosis. **v2c output is unchanged and that is MEASURED**, not argued: `TestV2cOutputUnchangedByV1Encoder` digests every shipped entry's v2c encoding, and the same digest was verified at the baseline commit in a worktree rather than merely recorded from the new tree.

**SNMPv3 notifications with USM (nl6#98).** `-trap-snmp-version v3` emits the SAME `0xA7` SNMPv2-Trap-PDU as v2c inside an RFC 3412 ScopedPDU and an RFC 3414 USM envelope. `trap_v3.go` ASSEMBLES; it contains no crypto and no BER of its own, because nl6#627 had already lifted the three seams it needs (`encodeNotificationPDU`, `wrapInScopedPDU`, `wrapScopedPDUInV3MessageWith`) and the instruction was to use them rather than re-lift or duplicate them. **THE ONE DESIGN DECISION IS THAT THE ENCODER HOLDS ITS OWN `*SNMPServer`, AND IT IS NOT THE DEVICE'S POLLING SERVER.** In nl6 `SNMPServer` IS RFC 3411's SNMP engine — it owns `usmServerState` and is the receiver the v3 envelope is a method on — and a notification originator IS an authoritative engine (RFC 3414 §2.1). So the encoder constructs one, private to itself, from the `-trap-snmpv3-*` configuration and a per-device engine ID. `usmState()` is UNTOUCHED: its engine ID is fleet-wide by explicit decision, and a one-line edit there would silently re-identify every POLLED device. The rejected alternative was parameterising `wrapScopedPDUInV3MessageWith` over an injected state, which reaches through `encryptScopedPDUAt`, `encryptDES`, `encryptAES128At`, `padData`, `encodeUSMSecurityParameters` and `encodeSNMPv3Message` — six more shipped-poll-path methods — to save one struct literal. **BECAUSE NO PRODUCTION POLL-PATH LINE CHANGED, "the poll path is byte-identical" is structural rather than argued**; the four nl6#627 baseline digests (measured in a worktree at `449280d`) still reproduce, and were re-run at this change's own baseline `e3c53c6` to confirm. **THE ENGINE ID IS DERIVED FROM THE DEVICE IP AND IS DELIBERATELY NOT CONFIGURABLE:** RFC 3411 §5 format 3, `80 00 7E D9 | 03 | 02 42 <ipv4>` — PEN 32473 (RFC 5612's documentation number, nl6#588's precedent, since nl6 has no PEN and will not claim another vendor's) plus `synthChassisID`'s MAC, so the trap identity is the identity the device already asserts over LLDP and in `{{.ChassisID}}`. Derived means DISTINCT, which is the whole point: localization is `H(Ku || engineID || Ku)`, so two devices sharing a user and password still key differently. **THE EMPTY-ENGINE-ID QUESTION WAS DECIDED, NOT INHERITED** (nl6#627 left it open): `wrapInScopedPDU` accepts a nil engine ID and `usmState` substitutes `defaultSNMPv3EngineID` for an empty one — both right for their own callers, both wrong here, because a fleet naming one default engine is the shared-identity defect of nl6#588/#599. A device with no derivable IPv4 is REFUSED at attach, and the construction ASSERTS that the engine settled on the derived octets rather than the substitute. **A COLLECTOR SEES TWO DIFFERENT `snmpEngineID` VALUES** for one device — the fleet-wide poll engine's and the device's own notification engine's. Correct per RFC 3414 and documented in `docs/reference/snmp-traps.md`, because it reads as a defect when debugging. **NO SNMPv3 INFORM:** an inform is authoritative at the RECEIVER (RFC 3414 §3.1), needing engine discovery and a key localized against each collector's engine, so it is refused at startup, at attach and at fire — the same three layers v1 uses, but with a DIFFERENT message at each, since v1 defines no InformRequest at all while v3 defines one nl6 cannot serve. **THE CHECK WITH DETECTION POWER IS `snmptrapd`**, not the in-package tests: `make test-interop` now runs both halves of net-snmp (`snmpget` polls, `snmptrapd` receives) across all seven auth x priv protocol combinations — the THREE RFC 3414 security levels, with both hashes crossed against both ciphers at authPriv — plus a wrong-password control and an end-to-end row fired through the exporter, and the CI gate installs the **`snmptrapd` package, which on Debian/Ubuntu is SEPARATE from `snmp`** — `snmp` is client tools only. The in-package tests decode with the independent BER reader, verify the digest against a key localized from the engine ID READ OFF THE WIRE (what a collector does, not what the encoder cached), and DECRYPT the scoped PDU from the RFC rules with an IV built from the advertised boots/time — which is what can catch the two-clock-reads class nl6's own decrypt path cannot see. **THE COST IS PUBLISHED, NOT DISCOVERED** (`trap_v3_bench_test.go`): v3 skips the allocation-free fast encoder (a v2c-only path by decision, as v1 also is), so a fire costs ~207-231 allocations against the v2c fast path's 33, while per-device SETUP is ~0.7 µs because `usmPasswordToKey`'s megabyte of hashing is cached fleet-wide and only the short localization is per device. **THE LOAD-TIME DATAGRAM BUDGET IS MEASURED AT THE FLEET'S OWN WIRE FORMAT**, and the first cut of nl6#98 got this wrong: `ApplySizeBudget` dry-rendered v2c unconditionally while the fire path encoded v3, and the USM envelope adds 91 bytes, so for a `-datagram-mtu` in the 1028..1119 band a v3 fleet disabled NOTHING, logged NOTHING and failed at EVERY fire into `send_failures` behind a `sync.Once` log — the nl6#487 silence that check exists to remove, reintroduced one version later. `ApplySizeBudgetWith` now takes a `notificationSizer` and `trapDryRenderSizer` picks it; an unrecognised version is an ERROR rather than a fall-through to the v2c measurement. v1 is deliberately sized AS v2c (its PDU is strictly smaller, so the figure over-estimates and can only disable an entry that would have fit — sizing it exactly would newly ENABLE entries). The v3 sizer measures through a REAL encoder with the msgID pinned at its widest, never through an estimate of what USM adds. **THE TEST'S v2c CONTROL IS WHAT MAKES IT MEAN ANYTHING**: asserting only that the Ciena entries are disabled under v3 is satisfied by a budget so low everything is disabled, so the same budget must leave them ENABLED under v2c. **STILL NOT IMPLEMENTED:** SNMPv3 INFORM (needs engine discovery), and RFC 7860's SHA-2 protocols / AES-192/256, which the poll path lacks too.
