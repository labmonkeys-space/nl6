# Dynamic IF-MIB counters and the interface-state clock



Extracted verbatim from `CLAUDE.md`, which exceeded the 150k-char auto-load limit. This is the long-form record: what the defect was, how it was found, and which mistake it is easy to reintroduce. `CLAUDE.md` carries the short invariants and points here.


**Dynamic IF-MIB counters (`if_counters.go`):** `IfCounterCycler.GetDynamic` serves every per-interface counter under `ifTable` (`.1.3.6.1.2.1.2.2.1`) and `ifXTable` (`.1.3.6.1.2.1.31.1.1.1`) analytically — no per-interface goroutine. `ifHCInOctets` / `ifHCOutOctets` are the master dial (sine wave, 60–100 % of `ifSpeed`, 1 h period); HC packet counters (ucast / mcast / bcast) derive from octets ÷ jittered packet size × jittered ratios; Counter32 shadow columns (`ifInUcastPkts`, `ifInMulticastPkts`, etc.) return the low 32 bits of the matching Counter64 HC column, and since nl6#570 that includes `ifInOctets` (ifTable `.10`, shadow of ifXTable `.6`) and `ifOutOctets` (`.16`, shadow of ifXTable `.10`) — every SHADOW column the cycler owns now derives from its HC column. (Not every Counter32 column of the two tables: `.12` `ifInNUcastPkts`, `.15` `ifInUnknownProtos` and `.18` `ifOutNUcastPkts` are deliberately unserved — no profile ships them and nothing derives them, so a walk omits them.) Before nl6#570 those two were absent from the list and served FROZEN from the profile JSON while `ifHCInOctets`/`ifHCOutOctets` on the same interface advanced at 200-400 Gbps, so a collector computing a rate from the 32-bit column got 0 bps forever and one cross-checking the two saw them disagree completely. **The low-32 equality is a DE-FACTO convention, not an RFC 2863 mandate** — the ifXTable DESCRIPTION calls `ifHCInOctets` "a 64-bit version of `ifInOctets`" and §3.1.6 mandates only which WIDTH to serve at which speed (32-bit octet counters at or below 20 Mb/s, 64-bit above, 64-bit packet counters at or above 650 Mb/s); a conforming agent may hold the two independently. Deriving one from the other is nl6's choice, and the first version of this paragraph asserted it as an RFC definition, which nl6#570's own issue text did too. **The shadow is DERIVED at read time from the same `t` the HC column used, never stored** — a second call to `deltaOctetsAt`, or a second clock read, reintroduces exactly the divergence the fix removes. **The identity is exact only for a caller that passes ONE `t` across both columns** (`GetDynamicAt`: sFlow `counter_sample`, gNMI). The per-OID SNMP path is NOT such a caller: `findResponse` calls `GetDynamic`, which reads the clock itself, and `NextDynamicOID` re-reads it per walk step, so a multi-varbind GET — or a GETNEXT/GETBULK, and nl6#542 made GETNEXT multi-binding — spanning `.10` and ifXTable `.6` samples two instants and drifts by whatever accrued between them (~5e7 octets per ms at 400 Gbps). That is a property of the read API, not of the derivation; capturing one instant per request would remove it and is a bigger change than nl6#570 took on. `TestOctetShadowThroughGetDynamicReadsTheClockPerCall` pins the caveat so the wording cannot drift back to an unconditional claim. `ifCyclerColumns` is in strict MIB lex order and doubles as the walk enumeration, so `.10` sits between `.9` and `.11` and `.16` between `.14` and `.17`; a wrong insertion point is a non-increasing walk (nl6#526's class, which no value assertion can see) rather than a wrong value, and `TestOctetShadowWalkOrderAndCompleteness` walks the real enumeration to pin it. The 1322 static entries the cycler now shadows (661 `.10` + 661 `.16`, across 20 profiles and 85 resource parts — issue #570's figure of 661 was ONE column) are DELETED, because `findResponse` consults the cycler first and dead data that looks authoritative is how this survived; the transition is recorded and reversed by `snmp_shipped_octet_shadow_ledger_test.go`, which reproduces the parent tag digest byte for byte, and nl6#541's ledger now chains off it (30 of its rewrapped NVIDIA rows are among the deleted ones, so its own reversal starts by restoring them). **The precondition for deleting a row is that the cycler knows its ifIndex**, and `InitIfCounters` builds that set EXCLUSIVELY from ifXTable `.6` keys bounded by `maxResourceIfIndex` — so the ledger asserts an HC `.6` row in the same profile for every deleted row (zero orphans across all 20), and a static `.10` for an ifIndex with no HC row is still SERVED, which is why the corpus guard checks that precondition instead of asserting unreachability. **The dead-data rule now covers EVERY cycler-owned ifTable column, and the one carve-out is the trap.** nl6#570 applied it to `.10`/`.16` only (its own Never clause forbade the rest); **nl6#574 deleted the other 742 rows** — `.9` `ifLastChange` (646 rows, 17 profiles), `.11` `ifInUcastPkts` (48, asr9k), `.17` `ifOutUcastPkts` (48, asr9k). `staticRowsOnCyclerOwnedIfTableColumns` now reads zero everywhere except `.7`/`.8`, so a non-zero entry is a regression rather than a backlog. **`.7` `ifAdminStatus` and `.8` `ifOperStatus` keep 887 static rows each and must NEVER be deleted** — they look exactly like the dead shadows and are not: `InitIfCountersWithScenario` reads both out of `oidIndex` via `ic.state.Seed`, so they are live input and deleting them changes every device's initial state. A carve-out on evidence, verified by reading the seed loop (which touches `.7` and `.8` and nothing else), and kept visible in the census rather than as a comment. `TestEveryDeletedDeadRowIsAnsweredByTheCycler` builds a real device per profile and requires `findResponse` to answer all 742 deleted OIDs — the defect-side guard, since the corpus digests' documented remedy is to RE-PIN, which is how an unreachable column would quietly become an unanswered one. The transition is recorded in `snmp_shipped_resource_defect_ledger_test.go`, ONE ledger for nl6#574 + nl6#571 + nl6#569 — 829 deletions and 5 value corrections in total (the mechanism is per-CHANGE, not per-issue: each data edit moves both golden digests and needs a chained reversal, and the sets overlap — `.25461.2.1.2.4.1.3` is both an nl6#569 invalid OID and an nl6#571 bare column), chaining back through every newer link to 44ef67f. **THE CHAIN IS STATED ONCE**, in the semantics paragraph in `context/snmp-vendor-arcs.md` — do not restate it here; this one was already two links stale. **Fleet-visible surface change:** 28 profiles ship HC `.6` rows but only 20 shipped static `.10`/`.16`, so 8 profiles GAIN two columns per interface — 452 OIDs no profile served before (`cisco_nexus_9500` +128, `juniper_mx960` +160, `cisco_catalyst_9500` +96, `palo_alto_pa3220` +32, three storage profiles +10 each, `linux_server` +6). The other 20 moved static→dynamic at an unchanged count, so an ifTable walk of `cisco_crs_x` (144 interfaces, the widest) returns exactly as many OIDs as before and SNMP-walk CPU figures taken on it stay comparable; figures taken on any of those 8 do not (nl6#517's convention). `createDefaultResources` — the compiled-in fallback written whenever a named resource file is absent, so a PRODUCTION path — gained ifXTable `.6.1`/`.10.1` rows and LOST its static `.10.1`/`.16.1`. Keeping those two was the first cut's decision and it was wrong: with no HC row no cycler is published, so they were served frozen forever, which is the 0-bps-forever defect itself shipping on the fallback profile while the docs claimed no static octet rows existed anywhere. With the HC rows present that profile now derives all four octet columns (speed from `ifSpeed.1`, 1 Gbps), and `TestDefaultResourcesServeOctetsDynamically` reads `.10.1` back through `findResponse` — that path had no test at all, so deleting or keeping those lines was invisible to verification. **The corpus guard that fires on the DEFECT rather than on a digest is `TestEveryInterfaceAnswersBothOctetColumns`**: it walks every shipped profile, builds a real device, and requires `findResponse` to answer both columns for every ifIndex the profile DESCRIBES (`ifDescr`, deliberately a different source from the cycler's own `ifHCInOctets` set, or the test would be tautological), floored at 1322 + 452 = 1774 answered instances. Without it, a later profile edit that adds interfaces without an HC row would silently drop both columns for them and the only tests to fire would be three corpus digests whose documented remedy is to RE-PIN — the nl6#541 glob hole again, a guard whose failure mode destroys the evidence. At 400 Gbps a Counter32 wraps in ~86 ms, so a collector polling these columns is misusing the MIB regardless (RFC 2863 says use the HC columns above 20 Mbps) — the fidelity value is that the stated contract is now true, not that the column is useful at that speed; error / discard counters derive from per-device ppm bands set by the `IfErrorScenario` field (`clean` | `typical` | `degraded` | `failing`). The same dispatcher powers the sFlow `counter_sample` body path in `counter_source.go`, so SNMP and sFlow values agree byte-for-byte at the same instant.

**The state engine's clock is injectable (nl6#575).** `InterfaceState` takes a now-source, normalised to `time.Now` at construction, matching the four other clock seams in the package (`flap_scheduler`, `syslog_scheduler`, `trap_scheduler`, `optical_alarm`) rather than inventing a fifth shape. **THREE reads move together and that is the load-bearing part**: `bootTimeUnixNs` is the origin every relative `lastChange` is measured from, so an engine whose boot time came from the real clock and whose transitions come from an injected one subtracts a real timestamp from a fake one, giving a garbage 58-bit value or a permanent rewind sentinel. **The sample stays INSIDE the CAS loop**, so a retry stamps the winning attempt; hoisting it reads as a harmless refactor and makes `ifLastChange` go backwards whenever REST and the flap scheduler contend on one interface (measured: 12,030 backwards reads in 100ms with 8 writers). That property had NO test until nl6#575's review demonstrated the whole package stayed green with the sample hoisted. **Why it exists:** `lastChange` is derived from the WALL clock (`UnixNano` strips the monotonic reading, and `wallRelNs` carries a rewind sentinel for the backwards step that follows), so a test asserting it is non-decreasing was asserting something the engine does not promise and could fail on any NTP step. **NOT `synctest`**, which nl6#575 suggested: a bubble serialises its goroutines, which would remove the real parallelism the flap test's torn-read assertions exist to exercise. An injected clock MUST return a positive `UnixNano`; a pre-epoch instant wraps `bootTimeUnixNs` and every transition then reports a rewind forever.
