# Dynamic IF-MIB counters and the interface-state clock

Moved from CLAUDE.md so the auto-loaded file stays under its size limit. Read this before changing the area it covers.

**Dynamic IF-MIB counters (`if_counters.go`):** `IfCounterCycler.GetDynamic` serves every per-interface counter under `ifTable` (`.1.3.6.1.2.1.2.2.1`) and `ifXTable` (`.1.3.6.1.2.1.31.1.1.1`) analytically — no per-interface goroutine. `ifHCInOctets` / `ifHCOutOctets` are the master dial (sine wave, 60–100 % of `ifSpeed`, 1 h period); HC packet counters (ucast / mcast / bcast) derive from octets ÷ jittered packet size × jittered ratios; Counter32 shadow columns (`ifInUcastPkts`, `ifInMulticastPkts`, etc.) return the low 32 bits of the matching Counter64 HC column, and since nl6#570 that includes `ifInOctets` (ifTable `.10`, shadow of ifXTable `.6`) and `ifOutOctets` (`.16`, shadow of ifXTable `.10`) — every SHADOW column the cycler owns now derives from its HC column. (Not every Counter32 column of the two tables: `.12` `ifInNUcastPkts`, `.15` `ifInUnknownProtos` and `.18` `ifOutNUcastPkts` are deliberately unserved — no profile ships them and nothing derives them, so a walk omits them.) Before nl6#570 those two were absent from the list and served FROZEN from the profile JSON while `ifHCInOctets`/`ifHCOutOctets` on the same interface advanced at 200-400 Gbps, so a collector computing a rate from the 32-bit column got 0 bps forever and one cross-checking the two saw them disagree completely. **The low-32 equality is a DE-FACTO convention, not an RFC 2863 mandate** — the ifXTable DESCRIPTION calls `ifHCInOctets` "a 64-bit version of `ifInOctets`" and §3.1.6 mandates only which WIDTH to serve at which speed (32-bit octet counters at or below 20 Mb/s, 64-bit above, 64-bit packet counters at or above 650 Mb/s); a conforming agent may hold the two independently. Deriving one from the other is nl6's choice, and the first version of this paragraph asserted it as an RFC definition, which nl6#570's own issue text did too. **The shadow is DERIVED at read time from the same `t` the HC column used, never stored** — a second call to `deltaOctetsAt`, or a second clock read, reintroduces exactly the divergence the fix removes. **The identity is exact only for a caller that passes ONE `t` across both columns** (`GetDynamicAt`: sFlow `counter_sample`, gNMI). The per-OID SNMP path is NOT such a caller: `findResponse` calls `GetDynamic`, which reads the clock itself, and `NextDynamicOID` re-reads it per walk step, so a multi-varbind GET — or a GETNEXT/GETBULK, and nl6#542 made GETNEXT multi-binding — spanning `.10` and ifXTable `.6` samples two instants and drifts by whatever accrued between them (~5e7 octets per ms at 400 Gbps). That is a property of the read API, not of the derivation; capturing one instant per request would remove it and is a bigger change than nl6#570 took on. `TestOctetShadowThroughGetDynamicReadsTheClockPerCall` pins the caveat so the wording cannot drift back to an unconditional claim. `ifCyclerColumns` is in strict MIB lex order and doubles as the walk enumeration, so `.10` sits between `.9` and `.11` and `.16` between `.14` and `.17`; a wrong insertion point is a non-increasing walk (nl6#526's class, which no value assertion can see) rather than a wrong value, and `TestOctetShadowWalkOrderAndCompleteness` walks the real enumeration to pin it. The 1322 static entries the cycler now shadows (661 `.10` + 661 `.16`, across 20 profiles and 85 resource parts — issue #570's figure of 661 was ONE column) are DELETED, because `findResponse` consults the cycler first and dead data that looks authoritative is how this survived; the transition is recorded and reversed by `snmp_shipped_octet_shadow_ledger_test.go`, which reproduces the parent tag digest byte for byte, and nl6#541's ledger now chains off it (30 of its rewrapped NVIDIA rows are among the deleted ones, so its own reversal starts by restoring them). **The precondition for deleting a row is that the cycler knows its ifIndex**, and `InitIfCounters` builds that set EXCLUSIVELY from ifXTable `.6` keys bounded by `maxResourceIfIndex` — so the ledger asserts an HC `.6` row in the same profile for every deleted row (zero orphans across all 20), and a static `.10` for an ifIndex with no HC row is still SERVED, which is why the corpus guard checks that precondition instead of asserting unreachability. **The dead-data rule now covers EVERY cycler-owned ifTable column, and the one carve-out is the trap.** nl6#570 applied it to `.10`/`.16` only (its own Never clause forbade the rest); **nl6#574 deleted the other 742 rows** — `.9` `ifLastChange` (646 rows, 17 profiles), `.11` `ifInUcastPkts` (48, asr9k), `.17` `ifOutUcastPkts` (48, asr9k). `staticRowsOnCyclerOwnedIfTableColumns` now reads zero everywhere except `.7`/`.8`, so a non-zero entry is a regression rather than a backlog. **`.7` `ifAdminStatus` and `.8` `ifOperStatus` keep 887 static rows each and must NEVER be deleted** — they look exactly like the dead shadows and are not: `InitIfCountersWithScenario` reads both out of `oidIndex` via `ic.state.Seed`, so they are live input and deleting them changes every device's initial state. A carve-out on evidence, verified by reading the seed loop (which touches `.7` and `.8` and nothing else), and kept visible in the census rather than as a comment. `TestEveryDeletedDeadRowIsAnsweredByTheCycler` builds a real device per profile and requires `findResponse` to answer all 742 deleted OIDs — the defect-side guard, since the corpus digests' documented remedy is to RE-PIN, which is how an unreachable column would quietly become an unanswered one. The transition is recorded in `snmp_shipped_resource_defect_ledger_test.go`, ONE ledger for nl6#574 + nl6#571 + nl6#569 — 829 deletions and 5 value corrections in total (the mechanism is per-CHANGE, not per-issue: each data edit moves both golden digests and needs a chained reversal, and the sets overlap — `.25461.2.1.2.4.1.3` is both an nl6#569 invalid OID and an nl6#571 bare column), chaining back through every newer link to 44ef67f. **THE CHAIN IS STATED ONCE**, in the semantics paragraph in `context/snmp-vendor-arcs.md` — do not restate it here; this one was already two links stale. **Fleet-visible surface change:** 28 profiles ship HC `.6` rows but only 20 shipped static `.10`/`.16`, so 8 profiles GAIN two columns per interface — 452 OIDs no profile served before (`cisco_nexus_9500` +128, `juniper_mx960` +160, `cisco_catalyst_9500` +96, `palo_alto_pa3220` +32, three storage profiles +10 each, `linux_server` +6). The other 20 moved static→dynamic at an unchanged count, so an ifTable walk of `cisco_crs_x` (144 interfaces, the widest) returns exactly as many OIDs as before and SNMP-walk CPU figures taken on it stay comparable; figures taken on any of those 8 do not (nl6#517's convention). `createDefaultResources` — the compiled-in fallback written whenever a named resource file is absent, so a PRODUCTION path — gained ifXTable `.6.1`/`.10.1` rows and LOST its static `.10.1`/`.16.1`. Keeping those two was the first cut's decision and it was wrong: with no HC row no cycler is published, so they were served frozen forever, which is the 0-bps-forever defect itself shipping on the fallback profile while the docs claimed no static octet rows existed anywhere. With the HC rows present that profile now derives all four octet columns (speed from `ifSpeed.1`, 1 Gbps), and `TestDefaultResourcesServeOctetsDynamically` reads `.10.1` back through `findResponse` — that path had no test at all, so deleting or keeping those lines was invisible to verification. **The corpus guard that fires on the DEFECT rather than on a digest is `TestEveryInterfaceAnswersBothOctetColumns`**: it walks every shipped profile, builds a real device, and requires `findResponse` to answer both columns for every ifIndex the profile DESCRIBES (`ifDescr`, deliberately a different source from the cycler's own `ifHCInOctets` set, or the test would be tautological), floored at 1322 + 452 = 1774 answered instances. Without it, a later profile edit that adds interfaces without an HC row would silently drop both columns for them and the only tests to fire would be three corpus digests whose documented remedy is to RE-PIN — the nl6#541 glob hole again, a guard whose failure mode destroys the evidence. At 400 Gbps a Counter32 wraps in ~86 ms, so a collector polling these columns is misusing the MIB regardless (RFC 2863 says use the HC columns above 20 Mbps) — the fidelity value is that the stated contract is now true, not that the column is useful at that speed; error / discard counters derive from per-device ppm bands set by the `IfErrorScenario` field (`clean` | `typical` | `degraded` | `failing`). The same dispatcher powers the sFlow `counter_sample` body path in `counter_source.go`, so SNMP and sFlow values agree byte-for-byte at the same instant.

**The state engine's clock is injectable.** `InterfaceState` takes a now-source, normalised to `time.Now` at construction, matching the four other clock seams in the package (`flap_scheduler`, `syslog_scheduler`, `trap_scheduler`, `optical_alarm`) rather than inventing a fifth shape. **THREE reads move together and that is the load-bearing part**: `bootTime` is the origin every stored `lastChange` offset is measured from, so an engine whose boot time came from the real clock and whose transitions come from an injected one subtracts a real timestamp from a fake one, giving a garbage offset (or, before the offsets became monotonic, a permanent rewind sentinel). **The sample stays INSIDE the CAS loop**, so a retry stamps the winning attempt; hoisting it reads as a harmless refactor and makes `ifLastChange` go backwards whenever REST and the flap scheduler contend on one interface (measured: 12,030 backwards reads in 100ms with 8 writers). That property had NO test until a review demonstrated the whole package stayed green with the sample hoisted. **Why it exists:** `lastChange` was derived from the WALL clock (`UnixNano` strips the monotonic reading, and `wallRelNs` carried a rewind sentinel for the backwards step that follows), so a test asserting it is non-decreasing was asserting something the engine did not promise and could fail on any NTP step. The offsets are now monotonic in production, and the seam stays: a clock built with `time.Unix` has no monotonic reading, so `Sub` falls back to the wall values the test chose. **NOT `synctest`**, which the original issue suggested: a bubble serialises its goroutines, which would remove the real parallelism the flap test's torn-read assertions exist to exercise. An injected clock no longer has to return a positive `UnixNano` for the offsets, which are computed on `time.Time`; `LastChangeNs` still wraps as a `uint64` for a pre-epoch boot, for a caller that reads it as a Unix timestamp.

**Counter hold while the derived oper-status is not up(1) (`if_counter_hold.go`).** The dial is a pure function of `t`, so the hold is a per-slot ledger `{down, downAt, upAt, skippedIn, skippedOut}` behind an `atomic.Pointer`, immutable once published, and the served delta is `delta(clamp(t)) − skipped`: `t` is clamped DOWN to `downAt` while down and UP to `upAt` always. `skipped` is the dial output over every COMPLETED down interval, so the counter resumes from the held value with no jump, and the dial being strictly increasing makes it monotonic by construction. It is applied at the ONE place `GetDynamicAt` reads the dial (`heldDeltasAt`, both directions under one bracket, replacing the two `deltaOctetsAt` call sites), so SNMP, both gNMI resolvers, dial-out and sFlow inherit it with no code of their own. The engine gains an unexported `onOper` hook set once at construction (same lifecycle as `setParents`), invoked from `Broadcast` beside the Tier C hook; it RECONCILES against the engine's CURRENT derived oper rather than trusting the event, so two hooks that race converge. `seedHolds` runs after `setParents` and before publish so empty bays, shut ports and children of a seeded-down parent read their base from the first poll; the default fleet moves at exactly 100 interfaces in 5 profiles (`shippedSeededNotUp`), and the up-only served-counter digest is byte-identical to the parent revision.

**Three things were found by the concurrency test, not by reasoning, and each is load-bearing.** (1) The hook's clock sample and a reader's are independent, so a reader that sampled AFTER the writer and loaded the ledger BEFORE the store served a value above the hold: 18,217 backwards reads in 200 ms of tight flapping. The write is now bracketed by `holdSeq`, a seqlock: odd, THEN sample the clock, store, even. A read that overlaps retries; one that completes with the old entry finished before the writer's sample. Readers pay two atomic loads and no write. (2) The mirror on CLOSE: a reader that sampled BEFORE the close and loaded the closed entry applied the new `skipped` to an older dial reading, below the held value. The entry records `upAt` and a read below it is clamped up. (3) `upAt` must be CARRIED across the next open, or a reader whose sample predates a close-then-open pair reads below the previous hold. Removing any one of the three fails `TestCounterHold_MonotonicUnderConcurrentFlaps` by thousands.

**The served-counter digest (`if_served_counter_digest_test.go`) normalises the dials.** Until nl6#989 `InitIfCountersWithScenario` drew phases, bases, packet sizes and ratios from the seeded RNG while iterating a MAP, so the draw order and every dial differed on every run and a digest over raw values never repeated (two runs on one build differed). The draws now run in ascending ifIndex order from `deviceSeed(IP)`, and `TestSameIPServesTheSameValuesOnEverySubsystem` pins that a device rebuilt from one IP serves identical values. The digest still overwrites every per-slot draw with a function of the slot and pins the serve ARITHMETIC alone, taken on the parent revision in a clean worktree before any production edit: a digest over raw dials would also move with every change to the generator or the seed derivation, which is a different measurement.

**Counter roll-up (`if_counter_rollup.go`).** A child (one lower layer: the `<port>.<unit>` name rule or one `ifStackTable` row) serves `share × parentServed(t)`; an aggregate (two or more active `ifStackTable` lower layers, `readStackLayers.members`) serves `Σ memberServed(t)`. **Composition is on the SERVED delta, after the parent's or member's own hold ledger, never on the raw dial**: on raw dials a child grows while its held parent stands still, which breaks the bound on every flap; on served deltas the bound holds by construction because shares sum below 1 and skipped totals are non-negative. `rawDeltaAt` is the composition and `heldDeltaFor` the ledger on top, so the recursion is child → aggregate → member at most and runs inside the one seqlock bracket. The child's own ledger stays and is nearly inert under a parent-driven hold (its skipped total grows by the dial output between the parent's and the child's hook instants, microseconds), and it is what holds a child alone under admin-down. Shares are `0.8/n` jittered ±20 % by an FNV hash of the ifIndex, not an RNG draw, so no other dial moves. **Bases and packet profile are inherited** (child: parent's packet size, mix, ppm; bases `floor(share × parent base)` per column; aggregate: members take the aggregate's profile, the aggregate's bases are the member sums) so the bound is exact on every Counter64 column; the Counter32 shadows wrap independently and carry no bound, and an aggregate's packet columns read the member sum plus at most (members − 1) because a floor of a sum exceeds a sum of floors. **The bound test asserts GROWTH as well as totals**: against a 24 h pre-seed, a child taking its parent's whole delta passed the total bound for hours, and the first mutation run showed it. The ASR 9902 bundle members are HundredGigE0/0/0/9 and 0/0/0/10 (ifIndex 10, 11), named in the xr-chassis model (`bundle_members`, validated: earlier physical port, listed once, speed sum equals the bundle speed) and rendered as two `ifStackStatus` rows, which `snmp_shipped_cisco_asr9902_bundle_members_ledger_test.go` reverses. The standalone-and-up served-counter digest was pinned on the parent revision and is unchanged; the shipped hierarchy is five profiles (`TestShippedHierarchyCountersRollUp` lists them). **A bundle's oper-status does not follow its members**: the engine follows one parent, stated in the docs rather than modelled.

**The generated profiles serve a complete `ifStackTable`, and the markers are silent.** junos-chassis and xr-chassis render `ifStackStatus.<unit or subinterface>.<parent>` from the same model entries that name them `<parent>.<n>`, plus the RFC 2863 markers `0.<I>` (nothing above) and `<I>.0` (nothing below) so every interface is in at least two rows; the rows agree with the name rule by construction, so `interfaceParents`, `NamedSubinterface` and every served digest are unchanged, and the served walk is pinned by `TestGeneratedProfilesServeACompleteIfStackTable`. `readStackLayers` skips a row whose lower layer is 0 BEFORE counting it in `rows[h]` and without a log line: it used to log "names an unknown lower layer" once per marker, 73 lines at the first Nokia device, and counting it would have demoted a child that also carries `<I>.0` to top-level through the "rows of which N resolve" branch. The OID NAME view is one set over the corpus, so the ledger's name reversal removes only the names Nokia did not already ship (`ifStackTableGeneratedNewOIDNames`), while the value view, keyed by profile, reverses every row.

**One boot instant per device, and a live `sysUpTime.0`.** `sysUpTime.0` used to be STATIC resource data: 26 profiles shipped a fixed value (asr9k 272922827, 31.6 days; check_point_15600 `0`) and five shipped none, so it never advanced, while every other clock of the device ran live and each took its own `time.Now()`. Measured in the lab before the change: a `coldStart` fired at 3622 ticks while a poll right after read 272922827, and `ifLastChange` read 3724 against the same static value, so a collector computing `sysUpTime - ifLastChange` placed a transition it had just triggered 31 days in the past. `DeviceSimulator.bootTime` is now stamped ONCE in `initDeviceCyclers`, the helper both creation paths call, before any engine or exporter exists, and passed to `NewMetricsCycler` as `MetricsCycler.startTime` (a parameter, so every caller chooses the origin explicitly); `InitIfCountersWithScenario` and `InitOpticalCycler` read that for `IfCounterCycler.startTime`, the state engine's boot origin (`newInterfaceStateBootedAt`) and the optical engine; the trap and syslog exporters take it through `BootTime` in their options and the flow exporter through `device.bootInstant()`; the poll engine's USM `bootedAt` reads `s.device.bootInstant()` inside its `sync.Once`, so engine time no longer starts at the device's first v3 message. `uptimeTicks` is the ONE formula behind the polled value, the trap varbind and `{{.Uptime}}`. Two clocks stay apart, by decision: the per-device SNMPv3 NOTIFICATION engine (`trap_v3.go`) has no device and counts from attach, which is creation; and hand-built fixtures with no boot instant answer `sysUpTime.0` from their resources, which is what keeps the wire digests deterministic. **A WALL-CLOCK JUMP used to separate two of the clocks, and the monotonic offsets joined them.** `sysUpTime.0` and the exporters subtract `time.Time` values that carry Go's monotonic reading, while the state engine stamped transitions with `UnixNano()`; a jump (an NTP step, a host suspend, a VM pause or snapshot: the monotonic clock stops while the wall clock moves on) then put every later `ifLastChange` AHEAD of `sysUpTime.0`. The slot now stores `sinceBootNs(bootTime, now)`, which is `now.Sub(boot)` clamped at 0, the expression `uptimeTicks` uses, and `ifLastChange` reads that offset directly (`lastChangeSinceBootNs`), so the two agree by construction. `LastChangeNs` keeps its meaning, absolute Unix nanoseconds, as `bootWall + offset`, so gNMI and NETCONF readers did not change; the cost is that after a jump of J their `last-change` is off by J against the notification's own wall-clock timestamp. **The rewind sentinel is GONE**: with both operands monotonic it was unreachable in production, and it leaked anyway (gNMI served `LastChangeNs` unchecked, so a rewind went out as `last-change = 18446744073709551615`); a clock reading before boot, which only a test clock can produce, now clamps to 0, and NETCONF sends the boot time where it used to omit the leaf. **The fix has no behavioural test and cannot have one**: public `time` APIs cannot build a `time.Time` whose wall clock jumped while its monotonic reading did not, so a mutator reverted to `UnixNano` passes everything that reads `lastChange`. `TestInterfaceStateMutatorsMeasureOffsetsOnTheMonotonicClock` is the guard: a `go/ast` check that `SetLinkState`, `setAdminLeaf` and `SetPeerDown` call `sinceBootNs` and never `UnixNano`, plus a check that a production-booted `bootTime` keeps its monotonic reading. On macOS the wall reading is microseconds and the monotonic one nanoseconds, so `bootWall + offset` can land up to a microsecond past a wall reading taken right after the transition; a test that brackets `LastChangeNs` between two wall readings must bracket the offset, and keep only a loose wall bracket on the absolute value (`TestInterfaceState_LastChangeNsAbsolute`). The guard covers `sinceBootNs`'s body (`now.Sub(boot)`, and no call that strips the monotonic reading: `Unix*`, `Round`, `Truncate`, `AddDate`, `UTC`, `Local`, `In`), the arguments its three callers pass (`s.bootTime` and the sampled reading, unmodified), and both clocks of a production engine (`bootTime` and `now()` carry `m=`); an independent review showed the first cut, which checked only "calls `sinceBootNs`, no `UnixNano`", missed a helper body computed on `UnixNano`, `Round(0)` arguments and a stripped transition clock, all green on Linux. Unchanged and still true: the offset wraps at 2^58 ns (about 9.13 years), which is not a multiple of the 2^32-tick `sysUpTime.0` wrap, so past 9.13 years of uptime `ifLastChange` would stop agreeing with `sysUpTime.0`. `ifLastChange` wraps at 2^32 with `sysUpTime.0` (`TestIfLastChangeWrapsLikeSysUpTime`); before the review of this change it was formatted unwrapped and, past 497 days, went out as an OCTET STRING. **Engine time from creation moves the fleet-wide engine ID trigger, it does not create it**: tested in review with SNMP4J 2.8.15 and 3.13.1 and net-snmp 5.6.2.1 on two devices sharing one engine ID, a manager that shares one engine-time table across devices (one SNMP4J USM, one libnetsnmp process) times out on a device whose engine time is more than 150 s behind the oldest it has seen, while one that starts from an empty table per poll is unaffected; the rule before this change failed the same way on first-contact spread. **The walk half is a separate, older defect.** `buildResourceIndexes` leaves `sysName.0` and `sysLocation.0` out of `sortedOIDs`, and since 7cf1b67 built `oidNextMap` from `sortedOIDs` the precomputed successor of `sysContact.0` has been `sysServices.0`; the GETNEXT fast path had no term for them, so a walk of the system group skipped both on 29 of the 31 shipped profiles (measured with net-snmp), while a GET answered them. `systemGapPreds`, computed once per resource set, names the static OIDs whose successor steps over a live system object, and the fast path checks the request against it by string equality rather than comparing OIDs on every walk step; `TestWalkDoesNotSkipSysNameOrSysLocationAlone` pins each of the two halves separately, because on a real profile the two objects are adjacent and either would cover for the other. The fix moved two wire digests (`TestWellFormedResponsesUnchangedOnTheWire`, 120 of 360 responses; `TestMultiBindingGetNextResponsesArePinned`, 60 of 72), and forcing the term clear brings both previous digests back byte for byte. The 26 shipped rows and the compiled-in fallback row were deleted, not corrected (`snmp_shipped_sysuptime_ledger_test.go`).
