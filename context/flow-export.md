## Flow export flags

```text
-flow-tick-interval <secs|dur>    # [seed]   Flow ticker cadence (default: 5s). This and the three flags below take a bare integer (seconds) OR a duration string (nl6#723); zero or less is refused at startup; sub-second values are accepted with no floor; a tick above 1h is still a logged fallback to 5s in WithFlowTickInterval, not a refusal. Honored since nl6#446 was fixed; applied at manager construction, NOT runtime-mutable. This is a BATCHING knob, not a volume knob: it sets how finely the stream is cut into datagrams. Volume is ConcurrentFlows / mean-flow-lifetime, so a slower tick makes bigger datagrams, not proportionally fewer records (a residual ~T/2 polling effect remains, because a flow sits cached up to one interval past its deadline). ONE simulator-wide ticker drives every device; per-device `tick_interval` is REJECTED with a 400 (nl6#445) rather than accepted and ignored.
-flow-active-timeout <secs|dur>   # [seed]   Cap on how long a still-running flow stays cached before export (default: 30s). Binds for ~92% of flows under the shipped profile. Sets a MEAN, not an exact deadline: each flow's deadline carries ±25% jitter (nl6#462), so 30s spreads expiry over 22.5-37.5s. Symmetric, so it moves emission SHAPE, not volume.
-flow-inactive-timeout <secs|dur> # [seed]   Idle time after a flow's last packet before export (default: 15s). Only reachable for flows shorter than (active - inactive), ~8% under the shipped profile. NOTE: before nl6#446 this was the ONLY timeout that could fire. `lastSeenAt` was pinned to flow creation, so every flow looked idle from birth and `-flow-active-timeout` was inert above this value.
-flow-tick-sync                   # [global] Sweep every device on the same ticker firing so the fleet exports in ONE burst per tick (restart-storm pattern). Default false: each device is swept once per period at its own phase (flow_tick_phase.go: 50 slots, 100ms firings at the 5s default, sub-period floored at 50ms), so a collector sees a near-flat arrival rate. Per-device batching, datagram sizes, the pacing sweep term and the flow digest are UNCHANGED; only fleet-wide alignment moves. The phase is a hash of the device IP, NOT an RNG draw (a draw would shift the flow stream, nl6#462). The scenario ticker takes the same slots. Latched with the period; GET /api/v1/flows/status reports tick_synchronized / tick_phase_slots from the latch.
-flow-nbar2                       # [seed]   Cisco AVC (NBAR2) IPFIX records (template 258) + RFC 6759 application table (259) from NBAR2-capable auto-start devices (cisco_ios, cisco_catalyst_9500 ONLY; curated in nbar2_capability.go, never by slug prefix). Requires -flow-protocol ipfix, -flow-collector AND an NBAR2-capable auto-start type: FATAL at startup otherwise, after -help/-version, before any subsystem. The auto-start batch is built as asr9k and no flag selects another type, so the flag is REFUSED on every boot today (the alternative was accepted-and-ignored, nl6#445); NBAR2 devices come from REST. Per-device via REST flow.nbar2. An incapable device in a mixed batch KEEPS its flow block and emits plain IPFIX (not flow's skip).
-nbar2-catalog <path>             # [global] Replace the embedded universal NBAR2 catalog (resources/_common/nbar2.json) AND every per-type overlay (resources/<type>/nbar2.json). Read once at startup; not reloaded by POST /api/v1/resources/reload. Oversized entries at the current -datagram-mtu are DISABLED and named at startup, never a boot failure.
-datagram-mtu <bytes>             # [global] Assumed MTU of the EGRESS path to collectors (default: 1500). EVERY UDP-emitting
                                  #          subsystem sizes datagrams to fit this frame. Flow does now, trap (#487) and SNMP
                                  #          GETBULK (#489) when those land. Lower it when the collector path is not standard
                                  #          Ethernet: a Docker overlay / VXLAN is typically 1450, tunnels lower. At 1450 on a
                                  #          1500-derived build, NetFlow v9 (1480), IPFIX (1484), NetFlow v5 (1492) and an
                                  #          OpenNMS-default GETBULK (1464) ALL fragment. Measured, not estimated.
                                  #          This is an assumption about a path nl6 does NOT control, not a property of its own
                                  #          interfaces (nl6 sets no MTU on TUN or veth; both take the kernel default 1500).
                                  #          NOT auto-discovered, deliberately: reading the route's interface MTU works for
                                  #          flow/trap/syslog (configured collector, known at attach) but NOT for SNMP, which
                                  #          answers whoever polls it and knows the destination only per request, so discovery
                                  #          cannot be the mechanism that covers every subsystem. No PMTU discovery either.
                                  #          Validated at startup (576..65535); an out-of-range value is fatal, not silent.
```

## Flow status counters (nl6#491)

**Flow status counters (nl6#491).** `sent_packets` / `sent_bytes` / `sent_records` on `GET /api/v1/flows/status` mean **reached the kernel**, and a refused datagram lands in the new `send_failures` instead. Before this they all incremented after a failed `WriteTo`, so the endpoint reported datagrams that never left the host and a down collector was undetectable from it. That is also why nl6#488's datagram gate cannot drive `Tick` through its probe socket (an `EMSGSIZE` never reaches the return value). This aligns flow with syslog, which already counted this way. `flow_sequence` still advances on a failed write, deliberately: reusing the sequence would hide the loss from the collector entirely, whereas advancing shows it as a gap. Changing that alters wire semantics and is a separate question.

## NBAR2: catalog, generation, config (Plan B and Plan C)

**NBAR2 (Plan B: catalog, generation, config).** `nbar2_catalog.go` is the THIRD catalog of the trap/syslog shape: `resources/_common/nbar2.json` embedded, `resources/<slug>/nbar2.json` overlays under `extends`, `-nbar2-catalog` replaces everything, loaded once at startup (`StartNbar2Catalogs`, budget passed explicitly after `SetLinkMTU`). **One `IPFIXAVCEncoder` is built per resolved catalog at load and shared by every device of that type**; `attachFlowExporter` swaps it in when `flow.nbar2` is set and hands the catalog to the exporter, while `buildFlowEncoder` stays the single source of truth for PROTOCOL names (NBAR2 is a record format under `ipfix`, not a protocol; the pool key and status row stay `ipfix`). **Generation inverts for NBAR2 devices**: `syntheticAVCFlow` draws the application by weight and the application FIXES protocol and port, then draws host and URI; `nbar2Catalog.draw` consumes exactly three RNG values on every call, list or no list (nl6#462's rule), and `syntheticFlow` is untouched. **Non-NBAR2 output is byte-identical by MEASUREMENT**: `flow_digest_test.go` drives the real `Tick` for 28 types × 4 protocols × option shapes with a held clock (`flowWallClock`) and compares against `testdata/flow-digests/pre-nbar2.tsv`, taken at the Plan A merge; regenerate ONLY for an intended wire change and say so. Two seams made the digest possible and both are wire-neutral: `flowWallClock` replaces seven `time.Now()` reads in the encoders, and `FlowCache.Expire` returns a tick's records in 5-tuple key order instead of map order. **The dry render DISABLES, never rejects**: an entry whose worst case (longest host + URI) cannot fit an empty datagram at the MTU budget is excluded from the draw AND from `Applications()` (so the table never advertises an id the device cannot emit) and named at startup; a catalog with zero usable entries refuses ATTACH, not boot. **Capability is curated** (`nbar2CapableTypes` / `nbar2IncapableTypes`, reason per row, completeness test), and the mixed-batch rule is deliberately NOT flow's skip: an incapable flow-capable device keeps its flow block and emits plain IPFIX with `nbar2` cleared (`degradeNbar2IfIncapable`, called from BOTH creation paths, pinned by a source scan since a batch needs root). **Shipped entries are all engine 3 with the port as selector**, which RFC 6759 defines; PANA-L7 selectors are unsourced protocol-pack data and are deliberately absent. **Plan C (ground truth and the external check).** The scenario report's `applications[]` key is `(l4_proto, dst_port, application_id)`: `application_id` is the WIRE value IE 95 carries, resolved through the participant's catalog AT LEDGER TIME and never the per-record index (an index means nothing outside one catalog, and two overlays can put different applications at index 1), captured on `scenarioPart` at `installScenPart` from the same field the exporter encodes with, so the report and the wire cannot disagree; 0 is a plain record (engine 0 is refused at load) and the field is `omitempty`, so a plain-only report is byte-identical to before. `l7_values[]` is a second fold keyed by `(application_id, field, value)` with `http_host` / `http_uri` and the four sent-basis counters; **its invariant is an INEQUALITY per field** against `applications[].records`, and the test carries both arms. `application_name` comes from a first-seen id→name table over the participants' catalogs, which is safe only because `nbar2CatalogsAgreeOnNames` pins every shipped catalog to agree. **The check with detection power is `make test-interop-ipfix`**: a real IPFIXcol2 (Debian forky's package, whose OWN libfds `cisco.xml` decides) resolves the PEN 9 elements BY NAME, decodes `applicationId` and the application table, and the report reconciles per key against the COLLECTOR'S decoded records with no tolerance; `en9:idNNNN` in its output is the failure signal. libfds types IEs 12235 and 9357 as strings and IPFIXcol2 DROPS non-printable bytes from a string unless `nonPrintableChar` is on (it is, in `examples/ipfixcol2/ipfixcol2.xml`; an earlier note here read the dropping as "cuts at the NUL"), so the gate sees every byte as a `\u00XX` escape and asserts the 12235 prefix and the 9357 hit count externally. Verified over veth at MTU 1500 / 1000 / 576: zero fragments, and NO shipped entry goes oversized at any legal MTU. The first capture found `resourceFileKey`'s defect: the flow / optical / NBAR2 gates run BEFORE `validateResourceFilename` and indexed their maps with the raw request string, so a bare slug got a capability verdict instead of the name error. **A real IOS-XE 26.01.02 capture is checked in** (`testdata/cisco-avc/capture/`, pinned by `cisco_avc_capture_test.go`, regenerable via containerlab): it CONFIRMS the 9357 layout and showed that 12235 is NOT a bare hostname (a constant six-byte `030000503402` prefix precedes the host and stands alone without one), which nl6 now emits from the single constant `avcHostPrefix` that the capture test also reads (nl6#679; a wire change that moved `plan-b-nbar2.tsv`); the router's record is a connection record with IE 12242 and a different field order, and a real NBAR2 table is two-thirds engine 13, which is the fidelity decision in nl6#680. Count-exact interop tests must run on Linux: the macOS-to-OrbStack loopback LOSES UDP at 200 devices.

## Datagram budget (nl6#485)

**Datagram budget (`flowPayloadBudget`, nl6#485).** Every sizing decision in `Tick` derives from `len(buf)`, so `Tick` reslices the pooled buffer to the collector's payload ceiling once, up front, and the flow loop, the sFlow counters loop and the options encoders all inherit it. The ceiling is the **frame** budget minus headers: `1472` for an IPv4 collector, `1452` for IPv6 (the family is resolved from the collector address, not assumed). The bug this fixes is the reason to keep the distinction sharp: `Tick` used to paginate against a full-MTU 1500-byte buffer, which spent the budget on the UDP *payload* and put NetFlow v9 at 1524 bytes and IPFIX at 1508 bytes on the wire, both fragmented. NetFlow v5 and sFlow escaped only by arithmetic accident (v5's 30-record protocol cap, sFlow's conservative 128-byte worst-case record), not by design, so neither is evidence the budget is right. **Fragmentation is invisible on LOOPBACK (MTU 65536), which is where every Go test sends. That, and only that, is why in-process measurement never caught it. veth DOES fragment** (kernel default MTU 1500), so nl6's own netns→veth path shows the bug plainly; an earlier note here claimed otherwise and made wire verification look like it needed hardware it never needed. `TestFlowDatagramsFitMTU` asserts the frame bound through the real `Tick` path, and a capture over veth confirms it. **Verified on the wire** in an Ubuntu VM (nl6#488): current `main` fragments 0 of 129 datagrams; emulating the pre-fix budget via `-datagram-mtu 1528` reproduces 85 of 212 (40%) with first fragments at exactly 1500 B, matching the original capture. On a link clamped to 1450, the default fragments 64/157 (40%) while `-datagram-mtu 1450` fragments 0/94. The MTU **is** a flag (`-datagram-mtu`) precisely because 1500 is an assumption about an egress path nl6 does not control.

## Flow application ground truth (scenario-app-traffic)

**Flow application ground truth (`scenario-app-traffic`):** flow-protocol scenario reports carry a fleet-wide `applications[]` block of sent-basis `bytes`/`packets`/`records` per `(l4_proto, dst_port)` plus `avg_bytes_per_second` (in-window bytes ÷ window; drain bytes count in totals but never inflate the rate), aggregated at the Tick write-return ledger hook via `scenarioPart.countApps` (set at `installScenPart`; sflow excluded, because its collector byte math is sampling extrapolation). Shipped `FlowProfile`s floor `SrcPortMin` at 49152 (IANA dynamic range) so random source ports can't collide with collector-side registered-port classification rules, and ICMP records carry zero ports (aggregating under `(icmp, 0)`). Both are wire-visible on all flow protocols. See `docs/reference/loadtest-report-schema.md`.

## Flow emission shape and pacing residency (nl6#462)

**Flow emission shape and pacing residency (`jitter-flow-active-timeout`, nl6#462):** the active-timeout deadline carries per-flow jitter of ±`flowActiveJitterFraction` (0.25), drawn **unconditionally** from the device's own `*rand.Rand` inside `GenerateFlows`' batch loop. Unconditional is load-bearing: a branch-dependent draw makes the RNG call count flow-dependent and desynchronises the stream, so a seeded run stops reproducing and `scenario-app-traffic`'s ground truth stops reconciling (`TestFlowJitter_DrawIsUnconditional` guards it; the app-traffic determinism test cannot, since it compares two runs of the same build). **Why jitter at all:** creation is driven by expiry (the cache refills exactly what it lost) and expiry was a deterministic offset from creation, so the creation profile was a pure delay of itself and any irregularity echoed every lifetime forever. Measured autocorrelation at one lifetime fell from +0.96 (GPU) / +0.87 (edge) to +0.17 / +0.23; `TestFlowEmission_EchoIsDamped` asserts it **relative to an undamped baseline it computes itself** via `FlowCache.activeJitterFraction`, not against a threshold, because profiles differ in how much echo they start with (campus is +0.54 undamped, its `DurationMax` sitting on the active timeout so most flows already leave by the self-damping inactive branch).

**The jitter exposed a pre-existing pacing error, and that fix is the load-bearing half.** `effectiveFlowLifetime(fe, sweep)` = `MeanFlowLifetime + sweep/2`: expiry is noticed by a periodic sweep, so a flow's real residency includes the mean wait for it. `flowPacingTarget` / `flowRateReachable` now take the sweep and divide by residency; `installScenPart` passes the SCENARIO's cadence (`scenarioFlowTickInterval`), not the fleet's, because that is what will actually drain the device. Two consequences: the documented per-device ceiling moved 8.5-9.7 → **8.1-9.2 records/s**, and paced runs stopped emitting a few percent low (nl6#462). The term was invisible before the jitter because deterministic deadlines on flows created at sweep boundaries expired at sweep boundaries, so the sweep cost exactly zero. That alignment was an artifact of synthetic timing, not a property of the exporter. **Do not fold the sweep term into `MeanFlowLifetime`**. That is a property of the profile and timeouts, while the sweep is a property of the exporter's cadence, and a scenario may sweep at a different cadence from the fleet.

## The FlowEncoder size extension point

The `FlowEncoder` interface has a `MaxRecordSize() int` extension point: fixed-size encoders return 0 (NetFlow5/9, IPFIX), variable-length encoders (sFlow) return a worst-case per-record byte bound that `FlowExporter.Tick` uses for MTU-safe pagination.
