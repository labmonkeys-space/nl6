## Architecture

**nl6** is a Go-based network device simulator capable of running 30,000+ concurrent simulated devices, each responding to SNMP (v2c/v3), SSH, and HTTPS REST protocols. It uses Linux TUN interfaces and network namespaces to give each device its own IP address.

### Package layout

| Path | Purpose |
|------|---------|
| `go/nl6/` | Core simulator — all device simulation logic and tests |
| `go/nl6/resources/` | 389 JSON files (29 device types) with SNMP/SSH/REST response data |

### Core simulator components (`go/nl6/`)

**Device lifecycle:** `simulator.go` (CLI/entry) → `manager.go` (SimulatorManager, shared keys/certs) → `device.go` (per-device startup, protocol server lifecycle)

**SNMP stack:** `snmp_server.go` → `snmp.go` (request handling) → `snmp_handlers.go` (OID lookup via sync.Map) → `snmp_response.go` (response building) → `snmp_encoding.go` (ASN.1 BER/DER).

**SNMP response size (nl6#489).** `maxSNMPResponseSize` is a FRAME bound derived from `linkMTU` and refreshed by `recomputeDatagramBudgets`, so it tracks `-datagram-mtu`; udp4 only, no address-family branch. **GETBULK truncates** (RFC 3416 §4.2.3 — a walk resumes from the last OID returned) but **GET and GETNEXT return `tooBig` with an empty binding list** (§4.2.1 — the requester has no resume point, so a partial answer is an undetectable wrong answer; GETNEXT joined this rule in nl6#542, which also means a single-binding GETNEXT that overflows now answers `tooBig` where it used to emit an over-budget datagram). All three PDU types share `createVarbindResponse`, deliberately (nl6#176: Enlinkd bundles three lldp OIDs in one GET), so the rule is an explicit `snmpOverflowRule` argument rather than something the encoder infers — getting it backwards is the most damaging mistake available here. Sizing is exact and incremental via `snmpMessageSizeFor`, never estimated: every bug in this family was a predicted size disagreeing with an emitted one. The GETBULK **walk** is separately clamped by `minVarbindSize` — a CPU guard, not a correctness one (a walk step is expensive; ~29 req/s already saturates cores on the LLDP path), deliberately an under-estimate so it never under-fills. **SNMPv3 GETBULK is bounded too, by MEASUREMENT rather than arithmetic** (nl6#535, see the nl6#517 paragraph): its envelope is not fixed, so the builder assembles the candidate through the real encoder and bisects to the largest prefix that fits; `max-repetitions` and `non-repeaters` are honoured there too (see the nl6#517 paragraph). `max-repetitions` is honoured at any width on the v2c path: the old parser read single-byte BER content only, so anything ≥ 128 silently became 10 — **benchmark numbers taken above 127 before this change are not comparable with numbers after it.** SNMPv3 is handled separately in `snmpv3.go` + `snmpv3_crypto.go` (MD5/SHA1 auth, DES/AES128 privacy).

**SNMP exceptions and SNMPv1 (nl6#517).** An OID absent from a profile is answered with the RFC 3416 `noSuchObject` exception (`80 00`), never `noSuchInstance` (a flat OID→value map cannot evaluate the prefix-registration test that separates them) and never a string. The exceptions travel from lookup to encoder as **sentinel strings** (`valueNoSuchObject`, `valueEndOfMibView`; `isSNMPExceptionValue`) that `encodeTypedValue` turns into tags — a value-space hazard (a resource value literally `noSuchObject` would encode as an exception; a v1 manager gets `noSuchName`) — see the resource value guard below. **SNMPv1 has no exceptions**, so a sentinel is diverted to `error-status = noSuchName` with `error-index` at the first offending binding and the request's names echoed with NULL values (RFC 3584 §4.2.2.2.1 noSuchObject, §4.2.2.2.2 endOfMibView). That diversion covers **GET and GETNEXT** in `createVarbindResponse`, selected by an explicit `v1DiversionRule` argument (`v1DivertSentinelAndCounter64` / `v1DivertSentinel` / `v1DivertNothing`): GETBULK is the one excluded, because it does not exist in v1 and its `oids` are walked, not requested, so echoing them would be neither the RFC 1157 echo nor bounded. It used to be GET-only, gated on `rule == overflowTooBig`, which worked only while GET was the sole tooBig caller; nl6#542 made GETNEXT multi-binding and therefore also tooBig, so the gate had to stop being a proxy for the PDU type. On the GETNEXT path the echoed names are passed SEPARATELY (`echoNames`), since its `oids` are the successors it found rather than the request's names. The GET echo deliberately skips the `snmpMessageSizeFor` budget — it is byte-for-byte the request's own varbind list, which the socket already accepted, and sizing it would produce a partial `noSuchName` echo. **SNMPv3 GET/GETNEXT go through `encodeTypedValue` too** (nl6#518): `createScopedPDU` is its third caller, so v3 carries the same tags as v2c and shares the value-space hazard. **v3 GETBULK terminates a walk (nl6#526).** `handleSNMPv3GetBulk` used to break on the `endOfMibView` sentinel without appending it, and with nothing collected the builder answered a placeholder `sysDescr.0 = "No data"` binding. Two things were wrong and the SECOND is what broke walks: a string stood where the exception belongs, AND `sysDescr.0` sorts BEFORE almost any requested OID, so snmp4j's `TreeUtils` saw a non-increasing OID and never finished. The v2c/v1 sibling placeholder at `snmp_response.go`'s `len(oids) != len(responses)` fallback is UNCHANGED and still answers `sysDescr.0 = "No data"`; it is a defensive branch for an internal invariant violation, not a reachable end-of-MIB path. The fix answers `{requestedOID, endOfMibView}` — **naming the binding with what was asked for is load-bearing**, since an exception on a wrongly-named binding fixes only half the problem (both mutations are pinned by `TestV3BulkWalkTerminates`). No encoder work was needed: nl6#518/#522 already route `createScopedPDU` through `encodeTypedValue`, so the handler discarding the sentinel was the whole defect. **nl6#535, done:** the response now carries EVERY binding the collection loop gathered, in order and each paired with its own value, and it is BOUNDED. The bound is measured rather than computed: the v2c path can size a response arithmetically because its envelope is fixed, but a v3 message's `msgGlobalData`/`msgSecurityParameters` sizes depend on engine ID, user name and privacy parameters, and under privacy the scoped PDU is padded to a cipher block. So the builder assembles the candidate through the REAL encoder and measures it, dropping from the end until it fits — a truncated GETBULK is resumable per RFC 3416 §4.2.3, and at least one binding is always emitted, matching the v2c carve-out. `createScopedPDUMulti` is now the single scoped-PDU builder and `createScopedPDU` delegates to it, and `wrapScopedPDUInV3Message` is the single envelope; both were split out precisely so the GETBULK path could not grow a second encoder to drift against, which is what nl6#529 and nl6#539 each cost. **`max-repetitions` and `non-repeaters` are now honoured** (nl6#535), which was safe to do only BECAUSE the bound landed first — that ordering was the whole point. Read via `parseBERInt` at ANY BER width: the v2c parser originally read single-byte content, so anything >= 128 silently became 10, and **benchmark numbers taken above 127 before that fix are not comparable with ones after it**. Both values are clamped at the PARSE SITE, since a negative reaching the handler is a negative loop bound on a serve path with no `recover()`. Two guards that no assertion about a response can see, so both are pure functions tested directly: `clampBulkWalk` bounds the WALK (the encode bound trims to the same bindings either way, so only the WORK differs — without it a request for 100000 costs 100000 `findNextOID` steps), and `largestFittingPrefix` BISECTS rather than descending (a descent fully builds and, under privacy, fully encrypts every over-budget candidate: O(n^2) bytes and n encryptions inline on the UDP handler at a real max-repetitions; measured at 12 builds versus 963 for 1000 candidates of which 37 fit). `len(resp)` is monotone in n, so bisection keeps the measure-never-predict property. **A multi-column GETBULK answers EVERY column** (nl6#535, last piece). `handleSNMPv3GetBulk` parses every variable-binding name via `parseAllOIDsFromScopedPDU` (the v3 sibling of `parseAllOIDsFromRequest`, sharing its `([]string, bool)` malformed-versus-absent contract and its list walker, `parseVarBindNames`) and applies the RFC 3416 §4.2.3 split: `non-repeaters` columns get one successor each, the rest are interleaved one binding per column per repetition, in the v2c `handleGetBulk` ORDER with the same per-column padding (an exhausted column's slots are named with its OWN requested OID, not the first column's). Serving one column also forced `non-repeaters` into `max-repetitions = 1`, which hid the M=0-WITH-non-repeaters row: those bindings are now returned instead of an empty list. **A MULTI-COLUMN v3 response is byte-identical to v2c, TAIL INCLUDED**, and the rule is keyed on LOOP SHAPE, not on version. An earlier cut of this change stopped once every column was exhausted and reported the difference as unavoidable; it was not. nl6#526's stop-instead-of-pad constrains the **single-column** loop only, so that loop still stops (a walk that runs out ships what it collected, and the next request gets the exception: `TestV3GetBulkShipsEveryCollectedBinding`, `TestV3BulkWalkTerminates`), while the multi-column loop pads every remaining repetition exactly as `handleGetBulk` does. The stated rationale for stopping did not survive either: a multi-column response already carries exception pads after real bindings inside every mixed repetition. Applying the single-column rule to a multi-column loop is pinned as a mutation by `TestV3GetBulkSingleColumnStopIsNotAppliedToMultiColumn`; the agreement is pinned by `TestV3GetBulkOrderMatchesV2c`, because each path being separately plausible is not the property. **That test asserts the full RFC 3416 count N + M×R as a PREMISE**, since the two paths measure against the same byte budget through DIFFERENT envelopes and a row large enough to truncate compares two different truncation points. What DOES still differ, and only on data that cannot load: `bulkStep` ends a column on the `endOfMibView` sentinel and on a non-advancing successor as well as on an absent one, and names that binding with the requested OID, where v2c's non-repeater loop tests only for an absent successor. Both extra exits are nl6#526/#524 properties a shared walk must not lose. `clampBulkWalk` now DIVIDES its ceiling by the repeater-column count: the work is columns × repetitions, so the guard keeps bounding the TOTAL (undivided it is C times looser, which is the amplification it exists to stop; applied to the total it is C times tighter and truncates a reasonable request). Neither mistake is visible in a response, since the encode bound trims to the same bindings either way, so it is pinned directly by `TestClampBulkWalkDividesByColumns`. The multi-column parse can only ADD discards (a LATER binding being malformed); it never relaxes nl6#547. **A declared CONTAINER length that overruns what contains it is MALFORMED, not absent** — the single most damaging thing this parser gets to decide. It used to be classified absent, so adding 8 to ONE length byte of a well-formed 3-column GETBULK made the parser report "no list here", the handler fall back to the dispatcher's single OID, and the response carry ten bindings from the first column: the nl6#535 defect restored verbatim by a one-byte lie, with no discard and no log line, while SHORTENING the same byte was already malformed. Both directions are now the same verdict, at every container, and every bound is written `n > len(buf)-pos` rather than `pos+n > len(buf)` because parseLength accepts a four-octet long form whose ADDITION can wrap negative on a 32-bit build and slip through an upper-bound test. Bytes between the end of the varbind list and the end of the PDU are refused too. The discard has its OWN `sync.Once` (`logFirstMalformedV3List`): sharing `logFirstMalformedV3` meant whichever of the two faults a device saw first silenced the other for the life of the process. **Multi-column is driven THROUGH the dispatcher** under noPriv, DES and AES128 (`TestV3GetBulkParamsSurviveTheDispatcher`), because the fallback is a legitimate branch: hand the parser the WRAPPED scoped PDU instead of the contents form and it reports absent, the handler answers the first column only, and every direct-call test stays green — nl6#527's failure shape on the same decrypt-unwrap seam. `handleGetBulk` now CALLS `clampBulkWalk` rather than inlining the identical expression, so the two cannot drift and the v2c side gets the column argument's wiring test too. The column COUNT itself has no explicit cap; what bounds it is the read buffer (`snmpReadBufferBytes`), and since the non-repeater loop walks once per column with no other bound, that coupling is pinned by `TestReadBufferBoundsTheColumnCount` rather than left implicit. `max-repetitions = 0` is answered as an EMPTY binding list (RFC 3416 §4.2.3, N = 0 and M = 0), via `createSNMPv3EmptyGetBulkResponse`, not through the builder's `len(oids) == 0` branch, which means end of MIB; conflating them told a walker the MIB had ended when nothing about the MIB was asked. `parseSNMPv3GetBulkParams` bounds its three INTEGER reads by the PDU's own length, not the datagram (the nl6#537 rule), and its post-tag checks are each reached by a committed seed (`brokenBulkScopedPDUs`, shared with `TestV3GetBulkMalformedParamsFallBack`). The clamp WIRING is pinned by `TestV3GetBulkClampsTheWalk` corrupting the successor one step past the ceiling and asserting `logFirstBulkAbort` never fires; the honoured value is pinned THROUGH the dispatcher under noPriv, DES and AES128 by `TestV3GetBulkParamsSurviveTheDispatcher`, because every earlier dispatcher test sent 10, which is also the parser's fallback. Two review findings landed with the bound: the ceiling is `min(budget, msgMaxSize)`, honouring the manager's declaration per RFC 3412 §7.1 with the §7.2 floor of 484 below which a declaration is ignored (`TestV3GetBulkHonoursManagerMsgMaxSize`); and the bound is pinned by a value-length SWEEP under noAuthNoPriv, DES and AES128 that also asserts the shipped bindings are the PREFIX of the unbounded collection and that the fit is maximal (`checkV3BulkBudget`), because at a single value length a builder that measured the bare scoped PDU, or that dropped from the HEAD, passed every test.

**Counter64 under SNMPv1 (nl6#524).** Counter64 does not exist in v1, and `encodeTypedValue` picks the tag from the OID alone, so a v1 GET of an `ifHC*` column used to answer tag `0x46` under `error-status = noError`. RFC 3584 §4.2.2.1 prescribes **two different behaviours, and the asymmetry is the whole design**: a **GET** diverts to `noSuchName` (same one-pass loop in `createVarbindResponse` as the sentinel diversion, so the FIRST offending binding wins whichever kind of offence it is), while a **GETNEXT SKIPS** the object and continues to the next successor, in `getNextBinding`. A GETNEXT names a position rather than an object, so erroring there would stop a v1 walk dead at the first HC column and truncate the table with no signal. `createSNMPResponse` must therefore NOT gain the diversion. **Since nl6#542 the two rules are an explicit argument, not an inference:** GETNEXT went multi-binding and therefore took the tooBig overflow rule, which is what the divert used to be gated on (`rule == overflowTooBig` meant "GET" only while GET was the only tooBig caller), so `createVarbindResponse` now takes a `v1DiversionRule` — `v1DivertSentinelAndCounter64` (GET), `v1DivertSentinel` (GETNEXT), `v1DivertNothing` (GETBULK) — alongside `snmpOverflowRule`. Same lesson as nl6#489: one encoder serving two rules takes the rule as an argument. Two properties worth keeping: the test is on the OID's DECLARED type, not on what the value encodes as (a Counter64 column holding a non-numeric value used to go out as a legal-in-v1 OCTET STRING and still diverts, because the MIB type is what a v1 manager cannot represent); and the GETNEXT path takes ONE `lldpServedOIDs()` snapshot for the first step AND the skip run, reused via `findNextOIDWithServed`, because calling `findNextOID` in a loop rebuilds the device's whole LLDP/ifAlias view per step (and two snapshots could straddle a topology generation bump). Walk order is column-major, so the Counter64 block is one contiguous run of (8 HC columns × interfaces), **1152 steps** on the widest shipped profile (`cisco_crs_x`, 8 columns x 144 interfaces, starting at `ifHCInOctets.1`), skipped once per binding. The figure lives in ONE place, the const `longestShippedCounter64Run`, and `TestLongestCounter64RunAcrossShippedProfiles` recomputes it over every directory under `resources/` except the `_`-prefixed ones, asserting EQUALITY (a run that got shorter is a stale document too, and it is now the numerator of the skip budget). **It is measured by WALKING `findNextOIDWithServed`, not by scanning `sortedOIDs`, and that is worth 4x.** The first pin scanned the static index and reported 288 — the same number the original hand measurement got, because both shared one blind spot: the walk also offers `ifCycler.NextDynamicOID`, since `IfCounterCycler` serves analytically the `ifXTable` columns a profile ships no JSON rows for. `cisco_crs_x` ships static rows for columns 1, 6, 10, 15 and 18 only, so `.7`-`.9` and `.11`-`.13` add 144 walk steps each and zero static ones. Every device has the cycler (both creation paths call `InitIfCountersWithScenario`), so 288 was never the number the loop walks; `TestStaticIndexUnderCountsTheCounter64Run` now asserts that the two measurements DISAGREE, so a future convergence has to be an explicit decision rather than a measurement quietly agreeing with itself again. The VERSION test comes first and is free (the request is already parsed at the top of `handleSNMPv2cRequest`), so a v2c fleet short-circuits on one integer compare and never reaches `snmpTypeTag`, which is a linear scan of the ~50-row type table that concatenates a string per row. Reversing those two operands would put that scan on every GETNEXT of every version. The skip loop is bounded twice (a non-advancing successor ends the walk, plus a per-DATAGRAM skip budget that backs up the comparison itself) because it runs INLINE in the shared UDP handler with no `recover()`: before this change a non-advancing `oidNextMap` was only the manager's problem, now it would wedge every device. Either bound is a data defect, logged once per device (`logFirstSkipAbort`, same gate as the trap path's `logFirstEncodeErr`) and answered as end-of-MIB, and `TestV1GetNextSkipLoopTerminatesOnNonAdvancingMap` pins both bounds by corrupting `oidNextMap` under a deadline. **A GETNEXT answers EVERY binding as of nl6#542** (RFC 3416 §4.2.2): the dispatcher parses the list with `parseAllOIDsFromRequest`, calls `getNextBinding` per name, and passes the request's names to `createGetNextResponse` SEPARATELY from the successors, because the v1 `noSuchName` echo must carry what the manager sent (RFC 1157 §4.1.3) while the bindings carry the successors. The single LLDP snapshot now covers every binding as well as every skip step. **Two CPU guards came with it, and the shape is nl6#535's in reverse.** A per-binding skip cap MULTIPLIES by the binding count where `clampBulkWalk` DIVIDES so its ceiling bounds the total, so the Counter64 skip allowance is a `counter64SkipBudget` shared by the whole datagram, and the binding count is clamped to `maxGetNextBindings()` (`maxSNMPResponseSize / minVarbindSize`, 98 at the default MTU) with anything above it answered `tooBig` WITHOUT WALKING — which is also the backstop that stops a larger read buffer raising the work linearly (the read buffer admits 68 names today, so it binds first). The budget is DERIVED, not hand-set: `maxGetNextBindings() * longestShippedCounter64Run`, exactly what the widest legitimate request needs, so it cannot truncate a real v1 table by construction. It replaced a literal 100000, which sat 1.28x above the real requirement once the run was measured through the walk — a profile with ~200 interfaces would have started truncating tables while every test passed. **The residual cost is real and is documented rather than hidden:** measured on `cisco_crs_x` with a live cycler, a v1 GETNEXT repeating one name before the HC block costs 2.9 ms at 1 binding, 27.2 ms at 10, 104.3 ms at 40 (a 752-byte datagram) and 176.8 ms at 68, inline on the shared UDP handler. What bounds that is the binding count, not the budget. An operator resource file with a wider Counter64 run than any shipped profile is the one case the budget does not cover; such a request truncates and is logged once per device. The regression that mattered was the single-binding case, essentially all real GETNEXT traffic, and it is byte-identical: `TestWellFormedResponsesUnchangedOnTheWire` excludes the one shape that legitimately changed (multi-binding GETNEXT, 72 of its 432 datagrams) and its digest was RE-DERIVED against baseline `5f3ca99`, not updated from the new code; the single-binding rows deliberately include a Counter64 column and a past-the-end name as well as a plain successor, since those are the corners this change touched, and the baseline produces the same digest over all of them. The 72 excluded ones are frozen separately by `TestMultiBindingGetNextResponsesArePinned` rather than left unexecuted. **One shape did move and is NOT byte-identical:** a single-binding GETNEXT that overflows the datagram budget now answers `tooBig` where `createSNMPResponse` applied no bound and emitted an over-budget datagram. Not reachable with shipped resources (no shipped value approaches 1400 bytes), reachable with an operator resource file, and pinned by `TestGetNextSingleBindingOverflowIsTooBig`. `createSNMPResponse` itself is now PRODUCTION-UNREACHABLE — its only caller is `createVarbindResponse`'s slice-length fallback, whose value is the literal `"No data"` — so the sentence above about it not gaining the Counter64 diversion is a statement about a dead path; the two copies of the v1 sentinel rule are held together by `TestBothV1SentinelDiversionsAgreeByteForByte` instead of by that warning. **Coverage is bounded by `oidTypeTable`** (the eight `ifXTable` HC columns); a 64-bit counter served under any other OID still reaches v1 as `0x46`. v1 GETBULK is deliberately untouched, for the same reason the sentinel diversion leaves it alone. Pinned by mutation rather than assertion alone: `TestV1WalkNeverReturnsCounter64` requires the walk to REACH the far side of the HC run, because absence of `0x46` is also satisfied by a walk that stopped at it, and four mutations are verified to fail the suite: removing the GET divert, giving the GETBULK call site a diverting rule (`v1DivertNothing` is what keeps it out; before nl6#542 the same property was carried by the `rule == overflowTooBig` conjunct, and only the COUNTER64 half of that wiring needed a new test — the sentinel half was already pinned by `TestGetBulkResponse_SNMPv1NotDiverted`), swapping the two behaviours, and over-skipping past the first non-Counter64 successor.

**SNMP resource value guard (nl6#523).** `validateSNMPResourceValues` (`resources.go`, beside `validateOpticalInventory`) rejects a resource response for which `isSNMPExceptionValue` is true, naming the file, the OID and the value. The test is EXACT, so `noSuchObject seen` and `NoSuchObject` are data; the error also says that omitting the entry is how you make an OID answer `noSuchObject` on purpose, since an absent OID already does. Scope is the `snmp` array only: SSH/API/Optical entries never reach `encodeTypedValue`, and the trap/syslog catalogs use a different encoder. Wired at the **four loaders a resource file can reach**. `createDefaultResources` writes compiled-in constants and is deliberately not guarded, since no input could make that check fire. Validated per JSON *part* in the two directory loaders, since a device-type directory holds ~15 split files and a post-merge check would name only the directory. `TestGuardIsWiredIntoLoaders` fails if any of the four calls is deleted (mutation-verified, with a positive control per loader asserting the fixture's exact entry count, so an unconditionally-erroring loader or one that dropped a part on merge could not pass). `TestSentinelValueWouldReachTheWireAsAnException` pins the sentinel set from the ENCODER side with literal strings and tags, so a third sentinel added to `encodeTypedValue` alone fails it. It is a refusal rather than the trap catalog's disable-and-warn because the rule depends on no operator-settable knob and the whole shipped set passes (`TestShippedResourcesLoadClean`, every `resources/` directory except the `_`-prefixed ones, asserting a non-zero entry count). **The remaining caveat:** the guard closes the **resource-file** route only. `sysName`/`sysLocation` are served outside the resource map, `sysLocation` coming from the operator-supplied worldcities CSV, and are not covered. **The nl6#529 OID-typed VALUE rule joins it:** a value on a leaf whose `snmpTypeTag` is `ASN1_OBJECT_ID` must be one `encodeOID` can represent. Encodability is decided by CALLING `encodeOID` and testing for the degenerate `06 00`, not by a second predicate — a second predicate that agreed on the day it was written is exactly how `trap_catalog.go`'s `validateDottedOID` drifted from the encoder (nl6#539), and `TestGuardAgreesWithTheEncoder` pins the property rather than trusting the comment. `06 00` is never a legitimate encoding (an OID has at least two arcs), so the signal is unambiguous. The sentinel rule is checked FIRST, matching `encodeTypedValue`'s order, so a sentinel on `sysObjectID` is diagnosed as the sentinel collision it would be on the wire (`TestValidateSNMPResourceValues_SentinelWinsOnOIDLeaf`). Coverage is bounded by `oidTypeTable`, which has one OBJECT IDENTIFIER row (`sysObjectID`). Both key spellings are exercised: `normaliseResourceOID` (shared with `buildResourceIndexes`) prepends the dot `snmpTypeTag` expects, so the undotted key tests the prepend and the dotted key its pass-through. `TestGuardAgreesWithTheEncoder` also pins the guard to the wire path (`encodeTypedValue` on the same key) and to `appendOID`, not only to `encodeOID`. OID **keys** remain unchecked. `TestGuardIsWiredIntoLoaders` now exercises BOTH rules across all four loader/layout combinations, because wiring is per RULE: a rule reached by only some loaders would pass a sentinel-only test. Still open from nl6#529 besides the guard: the value-slot OCTET STRING fallback (`encodeTypedValue`'s OID branch still emits `06 00` for an unparseable value); the trap catalog loader's second predicate is closed as of nl6#539 (see the trap catalog paragraph below). Nothing in the sentinel guard touches an encoder, so no wire behaviour changed for any input that loads today.

**The typed-class rule, and the widened Counter64 table (nl6#541).** `validateSNMPResourceValues` now carries a THIRD rule, and the three are documented in one place at `docs/reference/snmp.md` ("Resource values are validated at load") because nl6#541's stated complaint was that the gaps were scattered. Rule 3: a value on any leaf `oidTypeTable` types must encode AT that type, decided by CALLING the encoder (`encodeTypedValueAtTag`, the same dispatch the wire takes) and comparing the emitted tag with the declared one. The numeric and address branches fall through to `encodeOctetString` when `strconv`/`net.ParseIP` fails, which is the silent degradation that shipped nl6#515. **Two declared types are skipped**, because their branches cannot degrade and the loop runs over every entry of every profile on every load including per REST device-creation request: OCTET STRING (accepts anything) and OBJECT IDENTIFIER (answers an unrepresentable value with the degenerate `06 00`, whose tag IS the declared one — which is why rule 2 exists and cannot be folded in). Both skips are pinned against the encoder by `TestTypedClassSkippedBranchesCannotDegrade`, so neither can quietly become a hole. The rule INHERITS the encoder's asymmetries rather than tidying them: a negative on Counter32/Gauge32/TimeTicks LOADS (the encoder parses at 32-bit width and wrap-casts) while the same value on a Counter64 is REFUSED (no signed fallback). **That asymmetry has no shipped motivation** — an earlier draft of these docs claimed "several resource files use -1 as a placeholder" and that was fabricated: all 116 negative shipped values are `-1` on `ipRouteMetric1/2/3/5`, which the table does not type (RFC 1213 gives -1 as "not used" there), and ZERO sit on an unsigned 32-bit leaf (`TestNegativesOnUnsignedLeavesAreAbsent` keeps that honest). Since a wrapped `0xFFFFFFFF` is invisible to a collector in a way a dropped metric is not, such a value now draws a load-time WARNING rather than a refusal — a refusal would mean the guard no longer agreed with the encoder, which is the property that keeps them from drifting.

**The nl6#541 data edits, and what actually found them.** Applying rule 3 to the shipped set found 45 entries of the nl6#515 class: 14 × a bare `ipRouteDest` column OID valued `1` and 31 numeric overflows. **The other edits were NOT found by rule 3** and describing them as "32-bit-typed leaves" was wrong twice: five values past 2^32 (three `hrStorageSize`/`hrStorageUsed`, one PAN memory scalar) sit on leaves the table does NOT type, so rule 3 never saw them — `TestShippedBigValuesSitOnCounter64Leaves` found them; and `hrStorageSize.1 = 2147483648`, exactly one over Integer32 and one row above an edit made in the same change, was found by neither, because that test's threshold is 2^32. `TestShippedUntypedValuesFitInteger32` closes that band (an untyped numeric value must fit Integer32, RFC 2578) and is what caught it. Sixteen value edits in total carry no tag change; every one of them is an allocation-unit rescale keeping an `hrStorage` row internally consistent, or the PAN scalar. **The whole transition is committed as data and re-derived**, not summarised: `snmp_shipped_data_ledger_test.go` holds the 31 tag changes, 16 rescales and 14 removals machine-generated from a diff against `44ef67f`, reverses them against today's corpus, and requires the parent revision's digest byte for byte. A count is not a measurement a reader can check, which is the same standard the Block If sets for the table.

**Bare columns and over-specified instances, swept by nl6#571.** A varbind name must be an INSTANCE, with exactly as many trailing sub-identifiers as the table's INDEX clause says. Both failures ship in resource files and no load rule sees either, because the OIDs are well formed and the values encode fine: a BARE COLUMN has too few sub-identifiers (`…25.2.3.1.4` is the `hrStorageAllocationUnits` column), an OVER-SPECIFIED INSTANCE too many (`ciscoImageEntry`'s INDEX is one sub-identifier, so `ciscoImageString.2` is legal and `.2.2.1` is not). nl6#541's 14 `ipRouteDest` deletions happened because rule 3 REFUSED the value, not as a sweep; **nl6#571 deleted 61 entries — 57 bare columns across 14 distinct OIDs and 13 profiles, plus 4 over-specified `ciscoImageString` instances.** **THE DETECTOR IS A HEURISTIC AND IT INVERTED ON FIRST USE, which is the thing to remember here.** "Some other shipped OID extends it" proxies for "it is a column", and the proxy fails exactly when the EXTENDING sibling is the malformed one: all four Cisco profiles shipped `ciscoImageString.2` AND `.2.2.1`, the detector flagged `.2.2`, and the first cut of this change **deleted the legal name and kept the illegal one** in four profiles. Separating the two needs the table's INDEX ARITY, i.e. the MIB, which no test here has — so a hit is a CANDIDATE TO CHECK AGAINST THE MIB, never a verdict. **THE SCAN IS CORPUS-WIDE AND NARROWING IT IS THE REGRESSION TO GUARD AGAINST:** `TestBareColumnCensusHasNotGrown` looked for an extending sibling in the SAME profile and reported 41, while 20 entries were bare columns whose instantiated sibling lived in a DIFFERENT profile (bare `hrStorageAllocationUnits`; a bare Juniper `jnxOperatingCPU` column carried by four CISCO profiles; a bare PAN column carried by twelve NON-PAN profiles), so sweeping only the 41 would have driven the constant to 0 with 20 still shipping and a green suite. Legality is a property of the OID, not of which profile carries it. **That rule used to exist only as prose, and prose does not fail a build** — a review then demonstrated both guards could be narrowed back with the whole suite green, since a narrowing changes no shipped byte and so moves no digest and no ledger. Both now share ONE detector (`bareColumnsAcrossProfiles`) and ONE comparison (`bareColumnCountViolation`) and both open with `assertBareColumnDetectionIsCorpusWide`, a control that plants a column in profile A and its instance in profile B; the control it replaced planted both in the same set and therefore survived a narrowing. A test asserting ZERO of something cannot fail on its own — the control is what makes it able to. **The Block If was DECIDED as delete:** the bare `hrStorageAllocationUnits` entry in `cisco_catalyst_9500`, `cisco_nexus_9500`, `juniper_mx960` and `palo_alto_pa3220` was in each case the ONLY `hrStorageTable` row of any column, so deleting it empties the table rather than removing a duplicate — and a collector getting nothing is honest about a device type that models no storage, while a collector getting a binding named with a column OID gets a name that is not a legal instance. **Those four profiles now model no storage and that is CORRECT — do not restore the row to make the table non-empty.** **What NEITHER guard can see:** a bare column nothing in the corpus extends, an over-specified instance whose legal prefix is absent, and wrong INDEX arity generally (the under-specified `jnxOperating` tranche this used to file as open was CLOSED by nl6#602, which read the four-column INDEX clause out of JUNIPER-MIB; the class is open everywhere else). "The census reads zero" means no entry is an interior node of the shipped set — NOT that every shipped name is a legal instance.

**A trap and a poll must agree on type (nl6#593).** A trap catalog DECLARES a varbind's ASN.1 type; the resource `snmp` array SEPARATELY decides the type of a GET of that same OID. Two validation paths, and nothing joined them — so one profile could answer one object at two types depending on how it was asked. `cisco_ios` shipped it: `ciscoEnvMonSupplyStatusDescr.1` (`1.3.6.1.4.1.9.9.13.1.5.1.2.1`) declared `octet-string` by its trap, answered INTEGER by a poll, because the resource value was the string `"1"` and that OID is not in `oidTypeTable`. Found by hand in nl6#592 and fixed there; `TestTrapAndPollAgreeOnType` (`snmp_trap_poll_type_agreement_test.go`) closed the class, and that OID is pinned BY NAME as the regression anchor. **BOTH TAGS COME FROM THE PRODUCTION ENCODERS** — `encodeVarbindTyped` (plus `encodeVarbindTimeTicks`/`encodeVarbindOID` for the three the encoder prepends) and `encodeTypedValue` — and the trap side READS THE TAG BACK OUT of the encoded varbind rather than mirroring the encoder's switch. The type VOCABULARY is shared for the same reason: `trapVarbindTypes` in `trap_catalog.go` is the loader's own accept-set (`compileEntry` validates through `validTrapVarbindType`) and the guard's probe table is driven off it, so a ninth type there fails a test instead of quietly landing every varbind of that type in the encoder-failure bucket. **THE PROBE IS FOR TEMPLATED VALUES AND NOTHING ELSE.** Falling back to a probe on ANY encode error launders real defects into agreement: an `integer` varbind valued `"up"` fails at every fire and `ApplySizeBudget` disables the whole entry for an unrenderable one, yet re-encoding it with `"1"` would report AGREEMENT. The gate is `strings.Contains(value, "{{")`. **THE POLL SIDE HAS TO BE THE PRODUCTION POLL SIDE**, and two ways it is not both ship: a DUPLICATED OID (111 `(profile, OID)` pairs today — 64 `cisco_nexus_9500`, 32 `juniper_mx960`, 5 per `nvidia_*`, all `ifHighSpeed`, all identical values so nothing diverges yet) resolves LAST-wins after a NON-STABLE `sort.Slice` in `buildResourceIndexes`, and a SHADOWED OID is answered by `findResponse` ahead of `oidIndex` (`sysName.0`/`sysLocation.0`, which `buildResourceIndexes` does not even store; `getMetricValue`; `IfCounterCycler`; the interface-state override; LLDP/`ifAlias`). Both are REPORTED, never resolved by picking. **`_common/traps.json` is applied to EVERY profile** through the production resolver, and that arm is pinned BY THE CONTROL, NOT BY THE COUNTS — measured, not assumed: narrowing the join to `entry.fromOverlay` leaves every count unchanged and the package green, because all six real `_common` varbinds are templated and contribute zero occurrences. So the control substitutes a SYNTHETIC universal whose varbind carries a literal OID the plants serve. Same reason the entry check compares each universal entry's VARBIND SET, not its name: `MergeOverlay` replaces a same-named entry wholesale. **AN UNSERVED VARBIND IS NORMAL, NOT A FINDING**, and the claim is only that the profile serves no resource entry for it — this guard cannot read a MIB, so it must not be documented as saying those 182 are notification-only objects. The control has EIGHT ARMS (the nl6#605 lesson, extended): disagreeing pair reported, AGREEING pair silent, unencodable LITERAL reported as an encoder failure, DUPLICATE entry reported, SHADOWED OID reported as shadowed (its declared type deliberately AGREES with its value, so a rule that stopped honouring shadowing goes silent rather than reporting a different kind), an overlay that keeps a universal entry NAME while swapping its varbinds reported as drift, and nl6#607's typed-leaf pair (wrong type on a typed leaf reported, right type silent). Census constants, all re-derived each run: `trapCatalogVarbindsShipped` 191, `trapVarbindsWithTemplatedOID` 6, `trapPollJoinOccurrences` 185, `trapPollUnservedVarbinds` 182, `trapPollJoinedPairsShipped` (3 rows, BY IDENTITY — a count goes quiet on a swap), `trapPollPerCatalogCensus` (`{templated, examined, joined}` per file; ciena is 156 examined / 0 joined and that zero is asserted deliberately, since summed away a de-joining bug is indistinguishable from a genuinely disjoint catalog), `trapCatalogProfiles`/`trapProfilesCarryingUniversal` 29/29, `trapPrependedJoinedPairs` 24. That last covers `sysUpTime.0`/`snmpTrapOID.0`/`snmpTrapEnterprise.0` and FINDS NOTHING TODAY BY CONSTRUCTION (`oidTypeTable` types `1.3.6.1.2.1.1.3` TIMETICKS and the encoder prepends TIMETICKS) — coverage, not a near-miss. **What it CANNOT see:** it does not compare either side against a MIB (nl6#590's question — `jnxFruFailed` declares `jnxFruTemp`, a Gauge32, as `timeticks`, and no profile serves that OID so the join never reaches it); and a TEMPLATED OID is not joinable at all. **nl6#607 WIDENED IT TWICE, and NEITHER widening found a defect.** (1) A TYPED LEAF IS COMPARABLE WITH NO SERVED VALUE: `oidTypeTable` types the leaf, so the poll tag is `snmpTypeTag(oid)` and nl6#541's typed-class rule guarantees a loadable value encodes at it. Reported under its OWN kind (`findingTypedLeafDisagreement`) because the comparison changes shape, from "declared type versus the tag the SERVED VALUE emits" to "versus the tag the LEAF'S declared type emits". Conflating them makes both censuses meaningless. `trapPollTypedUnservedVarbinds` is **0 and 0 IS THE EXPECTED VALUE**: `oidTypeTable` types standard mib-2 leaves while trap varbinds name vendor notification objects, so the sets do not intersect. It is a tripwire, NOT a rule that found something, and a zero cannot fail on its own, so the control's arms 7/8 are the only thing that can make it fail. (2) A CATALOG MUST NOT CONTRADICT ITSELF (`TestTrapCatalogDoesNotContradictItself`): two varbinds of one EFFECTIVE catalog naming one OID at two declared types. It needs NO resource data, which is why it reaches two surfaces nothing else did: `ciena_waveserver5` (156 of 185 examined, joins ZERO, so its catalog had no internal check of any kind, and its four entries share one trap OID by design) and every TEMPLATED varbind, which the join cannot reach by construction, including the universal catalog's ENTIRE surface. Three load-bearing properties: the EFFECTIVE catalog not the overlay FILE (an overlay entry contradicting a universal varbind sits in a file that is internally consistent alone, and the control's third arm plants exactly that); PER DISTINCT CATALOG not per profile (26 profiles carry the universal unchanged, so a defect in it is ONE fact); and the tag resolved from the DECLARED TYPE via the probe, never from the varbind's value (a tag is a function of the type alone, and resolving through the value would turn an unencodable literal or a template into an encoder failure here, which is the join's finding and not this one's, and would leave the rule blind to the universal catalog). `trapCatalogSelfCensus` pins `{entries, distinct OIDs, OIDs carried by >1 varbind}` per catalog: universal 5/3/3, ciena 9/42/42, cisco_ios 12/17/3, juniper_mx240 12/16/5. **THE THIRD COLUMN IS THE ONLY ONE THE RULE USES**, since an OID carried by one varbind cannot disagree with itself, so a grouping collapse would drive it to zero while every finding count stayed zero too, which is exactly what that census exists to make visible.

**The widened Counter64 table.** `oidTypeTable` gained the 14 HC columns of each RFC 4293 IP statistics table and all 6 RFC 3635 `dot3HCStatsTable` columns — 34 rows, read out of the shipped MIBs with `snmptranslate` rather than recalled, because a hand-recalled list was wrong on every entry on the first attempt (and the comment claiming that provenance then itself misnamed the differing column as 22 rather than 2, which is the kind of error that costs a provenance claim its value). The test-side column lists are an independent RESTATEMENT, not independent VERIFICATION — both sides were written in the same change from the same reading — so that gap is closed by `TestOidTypeTableAgreesWithTheMIBs`, which compares the table against MIB facts EXTRACTED with net-snmp and checked in under `go/nl6/testdata/mibs/` (71 of the 83 rows resolve; 98 columns of the three widened tables, 34 of them Counter64). The fixtures carry the `snmptranslate` command that produced them and are read as data: the test does NOT shell out to net-snmp, because no workflow installs it and a `t.Skip` in CI asserts nothing. The 12 unresolved rows (the usmStats subtree prefix, OLD-CISCO freeMem, 10 LLDP-MIB columns) are COUNTED, so a new standard row cannot hide in that bucket. **Widening a type table is a WIRE change**, so it was measured: `TestShippedTagsUnchangedByTableWidening` hashes the (profile, OID, emitted tag) triples of all 27,318 shipped entries, and the digest taken BEFORE the widening still matches after it. **The effect of the widening on the shipped fleet is exactly zero** — no shipped profile serves any newly typed column, so its whole value is for operator files and for a future profile. The digest is keyed on the PROFILE as well as the OID deliberately: keyed by OID alone the 31 data tag changes vanish entirely (another profile already produced those pairs), and even the pair-set view showed only 12 lost pairs for 31 changed entries. It hashes tags, not bytes, which is what keeps it stable across ordinary data edits.

**The corpus guards must see BOTH layouts.** A device type ships as a directory of parts OR as a single `resources/<slug>.json`, and both are supported at all four loaders. The corpus walkers globbed `resources/*/*.json` — two path segments — so a vendor 64-bit column in a single-file profile passed the sentinel guard, the tag digest and the Counter64 pin, and **the only test that fired told the maintainer to re-pin a golden digest**, which would have absorbed the defect. `snmp_shipped_corpus_test.go` is now the one recursive walk every corpus test uses (`shippedResourceParts`, `shippedProfileNames`, `shippedSNMPEntries`), the two views cross-check each other, and `TestShippedCorpusViewsAgree` plants a single-file profile in a temp copy of the tree and requires the walk to see it. `TestLongestCounter64RunAcrossShippedProfiles` matters most here: its const is the numerator of `counter64SkipBudgetSteps()`, so an unmeasured long HC run in a single-file profile would under-size a serve-path budget and truncate v1 tables.

**`snmpTypeTag`'s scan.** It concatenated `prefix+"."` per row per call, and it runs once per encoded value on every response of every version — not only on the v1 GETNEXT path nl6#524 worried about. The comparison is now allocation-free. The evidence is a committed A/B over the SAME table (`BenchmarkSnmpTypeTagAB`: on an M1 Max at `-benchtime=200000x`, a full scan measures ~1170 ns concatenating and ~197 ns now) plus an equivalence pin (`TestSnmpTypeTagMatchesTheConcatenatingForm` over 840 boundary probes, `FuzzSnmpTypeTagFormsAgree` over 1.46M generated inputs). Absolute figures do not travel between machines; run the benchmark. An earlier draft of this file quoted three different numbers in three places, one of them (`~55 ns`) corresponding to no measurement of a full scan at all. This rewrite is not needed by the fix and ideally would be its own commit.

**`sysLocation` and `sysName` (part 3).** The sentinel rule for `sysLocation` is enforced ONCE AT LOAD (`dropSentinelLocations`), over the assembled slice, covering the CSV dataset and the compiled-in fallback alike. Putting it on the per-device draw instead cost up to 30,000 log lines at fleet start with the bad row still in the slice, and diverting a draw to `Unknown Location` silently discarded the device's coordinates; `getRandomLocation` keeps a bounded re-draw as the last-line assertion. **Dynamic IF-MIB counters (`if_counters.go`):** `IfCounterCycler.GetDynamic` serves every per-interface counter under `ifTable` (`.1.3.6.1.2.1.2.2.1`) and `ifXTable` (`.1.3.6.1.2.1.31.1.1.1`) analytically — no per-interface goroutine. `ifHCInOctets` / `ifHCOutOctets` are the master dial (sine wave, 60–100 % of `ifSpeed`, 1 h period); HC packet counters (ucast / mcast / bcast) derive from octets ÷ jittered packet size × jittered ratios; Counter32 shadow columns (`ifInUcastPkts`, `ifInMulticastPkts`, etc.) return the low 32 bits of the matching Counter64 HC column, and since nl6#570 that includes `ifInOctets` (ifTable `.10`, shadow of ifXTable `.6`) and `ifOutOctets` (`.16`, shadow of ifXTable `.10`) — every SHADOW column the cycler owns now derives from its HC column. Mutators are `SetOperStatus` / `SetAdminStatus` (CAS-loop, idempotent on no-op), fed by two sources: the flap scheduler (`flap_scheduler.go`, single shared min-heap goroutine driving Poisson-distributed flaps per (device, ifIndex) — same shape as `trap_scheduler.go`) and the REST control plane (`POST /api/v1/devices/{ip}/interfaces/{ifIndex}/{oper,admin}-status`). State transitions broadcast a `StateChange` event to every registered ON_CHANGE Subscribe listener via a per-stream depth-16 channel with drop-oldest on overflow. Cross-protocol consistency in Tier B: SNMP, gNMI Get, and gNMI Subscribe ON_CHANGE all see the same value at the same instant. **Tier C (`correlate-state-notifications`):** an oper-status transition now also fires correlated link traps + syslog for that ifIndex — `InterfaceState.SetNotify` installs an `atomic.Pointer[func(StateChange)]` hook invoked (oper-only, gated on `LeafOperStatus`) at the end of `Broadcast`, after the slot store commits. The manager wires it at trap/syslog attach time (`wireStateNotify`) to call `FireForInterface(entry, ifIndex)` on the role-matched catalog entries (`EntriesByRole`, vendor-wins-per-role); the closure snapshots the exporters under `device.mu.RLock` and fires outside the lock (closing-guard handles teardown). Covers all three mutation sources (REST, flap scheduler, REST auto-revert) via the single `Broadcast` funnel. Link telemetry volume now rides real state changes (`-if-flap-scenario` / REST), and state-driven fires bypass the Poisson global cap on initial transmit.

**REST auto-revert convention.** `POST .../oper-status` and `POST .../admin-status` accept an optional `duration` field (`{"status":"DOWN","duration":"30s"}`). When set: (1) the handler snapshots the pre-mutation slot value at POST time; (2) `SimulatorManager.revertTimers` registers the timer keyed by `(ip, ifIndex, isOper)` so a subsequent duration POST on the same leaf cancels the first; (3) `device.Stop()` cancels per-device timers, `manager.Shutdown()` cancels all; (4) `duration` is capped at 24h (`maxRevertAfter`) — over-cap returns 400; (5) on-demand HTTP fires bypass the flap scheduler's `-if-flap-global-cap` rate limiter, matching the trap/syslog convention for test-harness use.

**Metrics engine:** `metrics_cycler.go` drives 100-point pre-generated sine-wave patterns per device. `gpu_metrics.go` handles per-GPU metrics (utilization, VRAM, temperature, power, clocks). `device_profiles.go` defines per-category baselines.

**Network infrastructure:** `tun.go` creates TUN interfaces, `netns.go` manages the `nl6sim` network namespace, `prealloc.go` does parallel pre-allocation of TUN interfaces (configurable worker count 100–200) for fast scaling.

**Allocation-state locking on the device-creation path (nl6#556).** Which lock governs which field: **`sm.mu`** for `nextTunIndex`, `currentIP`, `tunPoolSize` and `maxWorkers`; **`tunPoolMutex`** for `tunInterfacePool` — its entries AND the map value, since a mutex that guards a map's contents does not guard replacing the map. Lock order where both are needed is **`sm.mu` → `tunPoolMutex`**, established by `shutdownFast`; `CleanupPreAllocatedInterfaces` therefore clears `tunPoolSize` under `sm.mu` BEFORE it takes the pool lock (doing it after left `GetStatus` reporting a pool size against an already-emptied pool for the whole duration of the bulk `ip -batch` delete). **No lock is held across interface CREATION** — not `ip link add`, `createTunInterface*`, or the `ip -batch` delete: the pre-allocator runs up to 500 workers and serialising them would destroy the feature. The claim stops at creation deliberately: `tunIface.destroy()` is a `syscall.Close` per interface and DOES run under `tunPoolMutex` in `CleanupPreAllocatedInterfaces`, and under both locks in `shutdownFast` — pre-existing, on shutdown paths, and untouched by nl6#556.

At the time of nl6#556 nothing excluded two concurrent creates from each other (`createBatchGate` now does — see nl6#565 below; `isCreatingDevices` is a UI status flag, `fleetFreezeCheck` only rejects during a scenario freeze window, and the auto-start goroutine runs alongside the HTTP server, so a pre-allocation batch really could overlap a `POST /api/v1/devices`). Within a batch the mechanism is still **reserve-then-work, not lock-around-work**, and it has to be, since the gate does not serialise a batch's own workers: `reservePreAllocBatch` commits `tunPoolSize`, `maxWorkers`, the `nextTunIndex` base and the batch's end `currentIP` in ONE `sm.mu` critical section BEFORE any worker starts, and returns the base, which the workers use to build their names. A worker must never read `sm.nextTunIndex` — reading it was the actual defect, since a concurrent `getNextTunName` moved the base mid-batch and two workers of the SAME batch could compute one name, failing the second `ip link add` — and the index and the IP must move in the same critical section so no reader sees one advanced against a stale other. Advancing at the START also stops the 5-minute timeout return from leaving the index behind interfaces already created (that timeout still DETACHES its workers, which keep creating interfaces after the caller has fallen back; the reservation is what makes that merely wasteful).

**What nl6#556 does NOT close: IP allocation.** Only the TUN index is genuinely reserved. `CreateDevicesWithOptions` rewinds `currentIP` to the batch start right after pre-allocation returns — necessarily, since the devices must land on the addresses the pool was created with — so `currentIP` is a shared cursor and two overlapping batches can still hand out overlapping device IPs. `tunPoolSize` and `maxWorkers` are likewise **last-writer-wins** across concurrent batches: batch A's `createDevicesParallel` can size its semaphore from batch B's worker count, and A's summary log can print B's numbers. Locking made those race-free, not correct. Closing either needs one-batch-at-a-time exclusion, which is a behaviour change, so nl6#556 reported it and **nl6#565 adopted it** (next paragraph).

**One creation batch at a time, and a concurrent one gets 409 (nl6#565).** `createBatchGate` (`types.go`, beside `isCreatingDevices`) is a `sync.Mutex` that `CreateDevicesWithOptions` **try-locks** at entry; a second concurrent batch is refused with the sentinel `errCreateBatchInProgress`, which `createDevicesErrorResponse` maps to **409 Conflict** via `errors.Is` (the nl6#538 `errResourceInvalid` shape) with `Retry-After: 5`. Fail-fast, not a queue: a 30k batch would make a small create wait minutes with no feedback, and an HTTP client that times out mid-wait cannot tell whether its batch ran. **This is a real API behaviour change** — two parallel `POST /api/v1/devices` used to interleave — and the `-auto-start-ip` batch counts as a batch, so a REST create issued during fleet startup 409s until startup finishes; `scripts/fleet.sh import` therefore RETRIES on 409 (`RETRY_409_LIMIT`/`RETRY_409_DELAY`), which is what keeps `compose up`'s bootstrapper working with an auto-start batch configured. The console's Clos wizard does not retry and leaves a half-built fabric; that is stated in `docs/reference/web-api.md` rather than fixed.

Four things are load-bearing. (1) The gate is **THE MUTEX and `isCreatingDevices` is THE STATUS FLAG**: the latter is an `atomic.Value` published AFTER entry and read by `fleetFreezeCheck`, so a check-then-set on it is racy by construction — it had already been mistaken for a lock once. (2) The gate must span **the reservation AND the IP walk**, which is why the body moved into `createDevicesWithOptionsLocked` and the wrapper holds the gate across the whole call with `defer` (panic included): gating only the reservation leaves the walk, where `currentIP` is actually consumed, unprotected, which is exactly the difference between nl6#556 fixing TUN naming and not fixing IP allocation. (3) It sits **above** the freeze check, above nl6#538's resource resolution and above the `isCreatingDevices` / `deviceCreateTotal` / `deviceCreateProgress` stores — a concurrency verdict must not depend on caller data, and a refused request must not clobber the RUNNING batch's counters or clear its freeze-interlock flag (the FR35/FR38 ordering inside the batch is unchanged). (4) The refusal reports the running batch from `createBatch`, a token published by `tryEnterCreateBatch` before the holder proceeds and cleared before its unlock, never from `deviceCreateTotal`/`deviceCreateProgress`: those are written inside the batch and never reset, so reading them stated a FINISHED batch's numbers as fact. `GET /api/v1/status` reports the same token as `create_batch_in_progress` / `create_batch_requested`, which is the poll signal a 409'd client should use — `is_creating_devices` is a proxy that can read false while the gate is held. The `currentIP` rewind is untouched and must stay: the devices have to land on the pre-allocated addresses.

**SCOPE: the gate is batch-versus-batch ONLY, and the first draft of this paragraph overstated it.** Three paths still mutate creation state outside it, all pre-existing and none gated here (a separate contract): a previous batch's **detached pre-allocation stragglers** — `prealloc.go`'s 5-minute timeout returns while its workers keep writing `tunInterfacePool`, so a straggler can overwrite the entry for an address the NEXT batch owns, leaking an fd and leaving two links on one IP; **`DeleteAllDevices`**, which clears `deviceIPs` and `tunInterfacePool` mid-walk; and **`Shutdown` / `CleanupPreAllocatedInterfaces`**, which zero `tunPoolSize` and clear the pool. For the same reason `tunPoolSize` / `maxWorkers` last-writer-wins is closed only against a concurrent BATCH, which is what `reservePreAllocBatch`'s comment now says.

**Testing this needed two production seams, because the first cut's tests had no detection power and its headline claim was false.** Deleting the gate from `CreateDevicesWithOptions` left three of six tests green — two of them pinned a hand-written MIRROR of the gated body, and the third's "gate is free afterwards" assertion is satisfied trivially by a batch that never took it. Worse, the claim that one test caught a release "moved before the walk" was false for the release point that matters: moved to sit after `PreAllocateTunInterfaces` and before the `currentIP` rewind — the nl6#556 boundary — the whole package stayed green, because that test's evidence was `isPreAllocating`, whose lifetime ends before the rewind. The seams: **`geteuid`** (indirects the privilege check, which sits ABOVE the rewind, so an unprivileged process returns before the half of the window this change is about — faked in BOTH directions, so the privilege-rejection path is exercised on a root CI container too instead of skipping) and **`createBatchStageProbe`** (nil in production; lets a test stand at `stageBatchEntered` / `stageAfterReservation` / `stageBeforeIPWalk` inside a REAL batch, ask whether the gate is held, and abort through the ordinary error return so the deferred release still runs). Every test now drives the real `CreateDevicesWithOptions`, and the gate is only ever observed through `tryEnterCreateBatch`, so a test cannot pass by reaching around a wrapper whose gate is gone. `TestGateIsHeldAtEveryStageOfTheBatch` is the pin for the walk claim, `TestGatedBatchesNeverOverlapOnDeviceIPs` for the defect (each of two racing batches must begin its walk at its OWN start address), `TestRefusedBatchTouchesNoCreationState` for (3), `TestCreateBatchGateIsReleasedOnEveryExitPath` for release on freeze / privilege / abort / panic. Verified by mutation at 20/20 detection over 20 runs each: gate deleted from the wrapper; release moved after the reservation but before the rewind; gate moved below the counter stores; release un-deferred; release at the end of the wrapper (panic only); refusal reading the stale counters; sentinel unclassified at the boundary. **Still not covered:** a batch driven to COMPLETION, which needs root and a Linux TUN device — every probe-driven test aborts before the first device is created, so the walk's own loop and `createDevicesParallel` are as untested as they were before.

`preAllocProgress` is an **Add-only** `atomic.Int64` (`bumpPreAllocProgress`), with `preAllocProgressBase` published per batch by `beginPreAllocProgress` and `GetStatus` reporting the difference. It was a load-then-store on an `atomic.Value`, which lost updates, AND was zeroed at the top of every batch, which both raced the workers' increments and wiped a concurrent batch's live count. Overlapping batches still share the one gauge, so status reports whichever baseline was published last — a display limit, not a lost count. The type change also removed the `.Load().(int)` assertion, so `GetStatus` no longer panics on a directly-constructed manager that never stored the field, which several test files build.

Pinned by `prealloc_locking_test.go`, which labels each test as a **race-detector pin** (only fails under `-race`: the worker-index, snapshot-accessor and cleanup tests) or a **value pin** (fails on an assertion either way: duplicate names, the torn `(index, IP)` pair, the progress counter, the IP walk). Every concurrency test in it needs a *spinning* counterpart goroutine with a `running` handshake before the code under test is called — a bounded loop of hand-outs finishes during the batch's own log lines and IP precompute, never overlaps the workers, and gives the detector nothing to pair (measured: 3 detections in 40 runs before the reshape, 20 in 20 after).

**Flow status counters (nl6#491).** `sent_packets` / `sent_bytes` / `sent_records` on `GET /api/v1/flows/status` mean **reached the kernel**, and a refused datagram lands in the new `send_failures` instead. Before this they all incremented after a failed `WriteTo`, so the endpoint reported datagrams that never left the host and a down collector was undetectable from it — which is also why nl6#488's datagram gate cannot drive `Tick` through its probe socket (an `EMSGSIZE` never reaches the return value). This aligns flow with syslog, which already counted this way. `flow_sequence` still advances on a failed write, deliberately: reusing the sequence would hide the loss from the collector entirely, whereas advancing shows it as a gap — changing that alters wire semantics and is a separate question.

**Datagram budget (`flowPayloadBudget`, nl6#485).** Every sizing decision in `Tick` derives from `len(buf)`, so `Tick` reslices the pooled buffer to the collector's payload ceiling once, up front, and the flow loop, the sFlow counters loop and the options encoders all inherit it. The ceiling is the **frame** budget minus headers: `1472` for an IPv4 collector, `1452` for IPv6 (the family is resolved from the collector address, not assumed). The bug this fixes is the reason to keep the distinction sharp: `Tick` used to paginate against a full-MTU 1500-byte buffer, which spent the budget on the UDP *payload* and put NetFlow v9 at 1524 bytes and IPFIX at 1508 bytes on the wire, both fragmented. NetFlow v5 and sFlow escaped only by arithmetic accident (v5's 30-record protocol cap, sFlow's conservative 128-byte worst-case record), not by design, so neither is evidence the budget is right. **Fragmentation is invisible on LOOPBACK (MTU 65536), which is where every Go test sends — that, and only that, is why in-process measurement never caught it. veth DOES fragment** (kernel default MTU 1500), so nl6's own netns→veth path shows the bug plainly; an earlier note here claimed otherwise and made wire verification look like it needed hardware it never needed. `TestFlowDatagramsFitMTU` asserts the frame bound through the real `Tick` path, and a capture over veth confirms it. **Verified on the wire** in an Ubuntu VM (nl6#488): current `main` fragments 0 of 129 datagrams; emulating the pre-fix budget via `-datagram-mtu 1528` reproduces 85 of 212 (40%) with first fragments at exactly 1500 B, matching the original capture. On a link clamped to 1450, the default fragments 64/157 (40%) while `-datagram-mtu 1450` fragments 0/94. The MTU **is** a flag (`-datagram-mtu`) precisely because 1500 is an assumption about an egress path nl6 does not control.

**Flow application ground truth (`scenario-app-traffic`):** flow-protocol scenario reports carry a fleet-wide `applications[]` block — sent-basis `bytes`/`packets`/`records` per `(l4_proto, dst_port)` plus `avg_bytes_per_second` (in-window bytes ÷ window; drain bytes count in totals but never inflate the rate), aggregated at the Tick write-return ledger hook via `scenarioPart.countApps` (set at `installScenPart`; sflow excluded — collector byte math is sampling extrapolation). Shipped `FlowProfile`s floor `SrcPortMin` at 49152 (IANA dynamic range) so random source ports can't collide with collector-side registered-port classification rules, and ICMP records carry zero ports (aggregating under `(icmp, 0)`) — both wire-visible on all flow protocols. See `docs/reference/loadtest-report-schema.md`.

**The scenario post-window phase is a BARRIER, not a duration (nl6#500).** A scenario submit's `drain` is REJECTED with a 400 — the newest member of the accepted-echoed-ignored family that `-flow-tick-interval`, `-trap-interval` and `-syslog-interval` already document (nl6#445). It never configured anything: `gateState.drainEnd` was written twice and read nowhere, `decide()` compares against `t1` only, and the window self-close timer uses the window alone. At T1 the terminal gate is published so no new fire initiates, and `finish()` then waits for the work ALREADY ADMITTED to return from its write — one write on the syslog/trap paths, one paginated `Tick` batch on the flow paths. Measured on syslog at T1 + 9ms with a 30s drain configured. The refusal keys on the KEY's presence (`json.RawMessage`, so `""`, `null` and a non-string value all 400 with the same actionable message), and it runs BEFORE the window parse so a body with both faults hears about the schema change first. The `drain` ledger bucket and the `drain_end` timestamp stay: both are observed, not configured. **The regression stop is BEHAVIOURAL** (`TestScenarioDrainEnd_IsTheReleaseInstantNotADeadline`: `drain_end` must equal the release instant under synctest) because a reviewer rebuilt the whole knob as `Grace` with a name-scanning test green; the identifier scan is a cheap second net only. **`closeAndWait` IS BOUNDED as of nl6#567**, and the BARRIER is what got bounded, not the transports. It gives up at `drainBarrierTimeout` (60s, PRIMARY not derived: an earlier cut wrote it as `2 * drainWatchdogInterval`, which meant lowering the watchdog to see the log sooner silently shortened the CEILING, to 10s at a 5s watchdog, below the write timeout it must clear; `TestDrainBarrierCeilingClearsItsInputs` asserts the relationships instead) and RETURNS the number of sends still in flight. **IT BOUNDS THE BARRIER, NOT SHUTDOWN, and the difference is the thing to remember here.** `finish()` joins the scheduler and the trap and flow tickers BEFORE the barrier and NONE of those joins has a ceiling; the syslog and trap schedulers fire INLINE, so a stalled SCHEDULER-DRIVEN write parks finalize at `c.sched.Stop()` and the ceiling is never armed. What the ceiling actually reaches is a fire admitted OUTSIDE the scheduler (REST on-demand, state-driven link notifications). Found by a test that hung for five minutes with `finish` blocked at `scenario_controller.go:1373`, after two reviewers independently flagged the ticker joins. Bounding those joins is **nl6#618**, not this change. Per-transport write deadlines were the rejected alternative: they cannot bound the total (syslog TCP serialises behind `writeMu`, so a device's worst case is 2s × the fires queued behind it) and they are blind to the case that has no deadline to set at all, namely an admitted fire that never calls `leave()` because its write path panicked or a callback was dropped. **THE STRAGGLERS ARE NOT CANCELLED and cannot be** (nothing interrupts a write parked in the kernel): they keep running and keep moving ledger counters after the snapshot. Those are atomics, so there is no race; what is lost is that `emitted` is incremented at GENERATION and `sent` at the write's RETURN, so a straggler sits between the two and the affected participant's identity may not hold. That is why the count is reported as its OWN field (`drain_stragglers`, `omitempty`, so a healthy report is byte-identical to before) and NEVER folded into `dropped` — a straggler may still reach the collector, so `dropped` would assert an outcome nothing observed. Production never checks the identity (every `identityHolds` call site is a test), so nothing fails on a live simulator. `drainGate` carries an `inflight atomic.Int64` shadowing the WaitGroup, because a `sync.WaitGroup` cannot be read. Three residuals, recorded rather than hidden: a truncated finalize leaves the `wg.Wait()` goroutine parked until its last straggler returns, or forever if one never does (one goroutine, per truncated finalize, on a shutdown path); `emitting` flips false while stragglers may still spend limiter tokens, so a peer starting then sees no contention; and `Shutdown` proceeds to tear down exporters while a straggler is still inside a write. **60s also exceeds `docker stop`'s default 10s grace**, so a containerised deployment may be SIGKILLed before the ceiling fires and write no report at all: raise `stop_grace_period` if a truncated report is worth more than a fast stop. Two races the review caught and the tests now pin: `leave()` does `wg.Done()` BEFORE the shadow decrement (the other order let the last fire read 0 while `done` was not yet closed, so a give-up in that window reported a truncated run as CLEAN), and the ceiling branch prefers a closed `done` because `select` picks at random among ready cases. The count is floored at 1 on the give-up path, which is an invariant and not a fudge: reaching that branch means `done` was not closed, so at least one fire had not called `wg.Done()`.

**Flow emission shape and pacing residency (`jitter-flow-active-timeout`, nl6#462):** the active-timeout deadline carries per-flow jitter of ±`flowActiveJitterFraction` (0.25), drawn **unconditionally** from the device's own `*rand.Rand` inside `GenerateFlows`' batch loop. Unconditional is load-bearing: a branch-dependent draw makes the RNG call count flow-dependent and desynchronises the stream, so a seeded run stops reproducing and `scenario-app-traffic`'s ground truth stops reconciling (`TestFlowJitter_DrawIsUnconditional` guards it; the app-traffic determinism test cannot, since it compares two runs of the same build). **Why jitter at all:** creation is driven by expiry (the cache refills exactly what it lost) and expiry was a deterministic offset from creation, so the creation profile was a pure delay of itself and any irregularity echoed every lifetime forever. Measured autocorrelation at one lifetime fell from +0.96 (GPU) / +0.87 (edge) to +0.17 / +0.23; `TestFlowEmission_EchoIsDamped` asserts it **relative to an undamped baseline it computes itself** via `FlowCache.activeJitterFraction`, not against a threshold, because profiles differ in how much echo they start with (campus is +0.54 undamped, its `DurationMax` sitting on the active timeout so most flows already leave by the self-damping inactive branch).

**The jitter exposed a pre-existing pacing error, and that fix is the load-bearing half.** `effectiveFlowLifetime(fe, sweep)` = `MeanFlowLifetime + sweep/2`: expiry is noticed by a periodic sweep, so a flow's real residency includes the mean wait for it. `flowPacingTarget` / `flowRateReachable` now take the sweep and divide by residency; `installScenPart` passes the SCENARIO's cadence (`scenarioFlowTickInterval`), not the fleet's, because that is what will actually drain the device. Two consequences: the documented per-device ceiling moved 8.5-9.7 → **8.1-9.2 records/s**, and paced runs stopped emitting a few percent low (nl6#462). The term was invisible before the jitter because deterministic deadlines on flows created at sweep boundaries expired at sweep boundaries, so the sweep cost exactly zero. That alignment was an artifact of synthetic timing, not a property of the exporter. **Do not fold the sweep term into `MeanFlowLifetime`** — that is a property of the profile and timeouts, while the sweep is a property of the exporter's cadence, and a scenario may sweep at a different cadence from the fleet.

**SNMP trap export (per-device config, phase 4):** `trap_manager.go` (SimulatorManager integration, `TrapSubsystemConfig`, `StartTrapSubsystem` / `StopTrapExport`, HTTP handlers' helpers, `TrapStatus`) + `trap_catalog.go` (JSON catalog loader with embedded universal set + weighted-random pick + `text/template`-based varbind resolution) + `trap_v2c.go` (SNMPv2c TRAP [0xA7] and InformRequest [0xA6] PDU encoder, GetResponse [0xA2] ack parser — reuses `snmp_encoding.go` ASN.1 primitives) + `trap_scheduler.go` (single central min-heap scheduler goroutine with Poisson inter-arrival + `golang.org/x/time/rate` global cap) + `trap_exporter.go` (per-device `TrapExporter` with atomic per-device UDP socket, bounded pending-inform map with oldest-drop, reader/retry goroutines in INFORM mode). **Trap operational notes:**
- **`maxTrapPDU` is a FRAME bound, derived, not a literal (nl6#487).** It is `linkMTU - ipv4HeaderBytes - udpHeaderBytes` (1472 at the default MTU), registered in `recomputeDatagramBudgets()` so it tracks `-datagram-mtu`. It was previously a literal 1500 justified as "matches the buffer the legacy path allocated" — the same payload-versus-frame conflation as nl6#485, which put a full-size trap at 1528 B on the wire. **Wire-verified:** an entry sized between the two bounds fragments 40/40 datagrams under the old bound and is refused under the new one. No address-family branch (unlike flow), because trap collectors resolve `udp4` only. Three sites read it and must stay in agreement: the `trapBufPool` allocation, the reference-encoder scratch clamp (both `trap_exporter.go`), and the encode guard (`trap_encode_fast.go`).
- **Two size enforcement points; the load-time one DISABLES rather than rejects.** Catalog load dry-renders each entry (worst-case context INCLUDING a worst-case `{{.Detail}}` and a max request ID — rendering `Detail` empty let a Raise entry pass load and fail at every fire while its Clear was disabled, which can strand an alarm) and marks anything over budget `oversized`: it stays in the catalog but is excluded from BOTH `Pick` and `EntriesByRole`, and is named once at startup. Filtering only `Pick` would leave an oversized `linkDown` firing on every oper-status transition. Loading does NOT fail, because the budget follows an operator-settable MTU — rejecting would make any `-datagram-mtu` below ~1004 refuse to boot on nl6's own shipped optical catalogs, which the operator can fix from neither side. The fire-time encode guard remains the backstop for runtime `{{.Detail}}` and REST `varbindOverrides`, which a load-time render cannot bound.
- **Lowering `-datagram-mtu` disables shipped optical trap entries.** The Ciena `opticalPreFecS[DF]{Raise,Clear}` alarms carry 39 varbinds and encode to 989-1000 B once `{{.Detail}}` and a worst-case request ID are accounted for, so below roughly MTU 1028 they stop firing and are named in the startup log with the size, the gap, and the MTU that would admit them. If optical alarms go quiet after an MTU change, that log line is the answer.
- `TrapSubsystemConfig.PDUBudget` is **required** and passed explicitly by the caller after `SetLinkMTU` has run; a non-positive value is rejected rather than defaulted. The loader does not read the global, so a size check cannot silently run against the default MTU if startup order changes.
- The fire-path resolve/encode error log is `sync.Once`-gated per exporter (`logFirstEncodeErr`), matching `firstWriteErr`. Ungated it was ~1,000 lines/second at 30k devices for a defect present since startup. `sendFailures` still counts every occurrence — only the log line is suppressed.
- INFORM mode (`-trap-mode inform`) requires `-trap-source-per-device=true` (the default) so the per-device UDP socket can demux acks without a global request-id table. Enforced at device-attach time (phase 4 moved it out of startup).
- Pending-inform map is bounded at 100 per device with oldest-drop overflow policy (exposed as `informsDropped` in `GET /api/v1/traps/status`).
- Retransmissions consume global-cap tokens (design decision to prevent retry-storm amplification when the collector is unreachable).
- Collector-side `rp_filter` may need relaxing (`net.ipv4.conf.*.rp_filter=0` or `2`) to accept UDP/162 with 10.42.0.0/16 source IPs — same caveat already documented for flow export.
- Per-device UDP source binding reuses the same `setupVethPair` + `FORWARD -i veth-sim-host -j ACCEPT` iptables rule that flow export already relies on. No new netns / iptables surface.
- **`StopTrapExport` is shutdown-only** (phase-5 review D1). It is not safe to race concurrent device creation: `startDeviceTrapExporter` captures scheduler / pool / encoder pointers under a short RLock and uses them outside that lock, so a concurrent Stop can leave orphan exporters or closed sockets. Today it is only called from the process-exit signal handler. Do not introduce a runtime "restart trap subsystem" control path without first tightening the attach-path lock discipline.

**Syslog transport seam (`add-syslog-tcp`, nl6#92):** `SyslogTransport` (`syslog_transport.go`) sits UNDER the write; catalog resolution, template vocabulary, the scenario gate and ledger accounting stay above it and are transport-independent. `udpTransport` is the datagram path byte-for-byte (including the per-device-bind → shared-pool ladder); `tcpTransport` (`syslog_transport_tcp.go`) is RFC 6587. Same shape as `DialoutTransport`. **TCP is deliberately NOT symmetric with UDP:** it has no shared-socket rung, because one connection carrying several devices multiplexes them into a framed stream with no field to demultiplex on — so a failed connection refuses the attach, and `-syslog-source-per-device=false` makes a TCP attach FAIL rather than degrade. Three things are load-bearing and non-obvious: (1) `SO_SNDBUF` is capped at 16 KiB because Linux auto-tunes to ~4 MiB per connection and this opens one per device (~117 GiB at 30k devices); (2) every write carries a deadline, because the syslog scheduler fires INLINE for the whole fleet so one stalled collector would stop every device; (3) only a read ERROR counts as connection loss — a collector banner would otherwise cause a permanent connect/drop loop. `sent` means "handed to the kernel" on TCP, not "on the wire"; status rows carry `transport` so TCP and UDP devices do not merge. **`maxSyslogMessageBytes = 1400` is a DATAGRAM bound that applies to every catalog regardless of transport** — deliberately, since the check is a once-per-entry dry render at load and making it transport-aware would defer it to a per-device runtime failure.

**Syslog TLS (`add-syslog-tls`, nl6#93):** there is NO `tlsTransport` type — RFC 5425 IS RFC 6587 inside a TLS session, so TLS decorates the DIALER (`syslog_transport_tls.go`) and `tcpTransport` is reused whole. **nl6 is the CLIENT: it verifies the COLLECTOR (`tls.ca_pem` INLINE / system roots / explicit `insecure_skip_verify`) and presents no cert.** The CA is inline PEM, not a path, because the per-device config is REST-settable and a path there is an arbitrary-file-read primitive (CodeQL `go/path-injection`); a path survives only as `-syslog-tls-ca`, read once at startup by `loadSyslogTLSCAFile`. The issue asked which cert to present — that misreads the direction; `sharedTLSCert` is a SERVER identity and is relevant only under mTLS, which is rejected until implemented. **The trap to know:** `dialOnce` caps `SO_SNDBUF` and sets keepalives via `c.(*net.TCPConn)`, which a `*tls.Conn` does not satisfy — so the TLS dialer calls `applySyslogTCPSocketOptions` on the raw socket BEFORE wrapping. Skip that and every TLS device silently inherits Linux's ~4 MiB auto-tuned buffer (~117 GiB at 30k devices). Port defaults to 6514 vs 514, so a bare hostname changes port when the transport changes. TLS record buffers are per connection and ADDITIONAL to the socket buffer, so the plaintext fleet-memory figure does not carry over.

**gNMI optical serving (`/components` branch):** `Resolve` and `ClassifyLeaves` dispatch on `elems[0]` — `interfaces` for the packet surface, `components` for the optical one, everything under the single prefix `/components/component[name=$och]/optical-channel/` (`optical-channel` augments `/components/component`, so one branch suffices). `gnmiOpticalLeaves` is the served contract, classified by container shape: `opticalLeafScalar` (in **both** `config/` and `state/`), `opticalLeafStats` (`state/<leaf>/{instant,avg,min,max}`), `opticalLeafCounter` (`fec-uncorrectable-blocks` — a **bare** leaf; asking for `/instant` on it returns a `NotFound` that says why, because that is the mistake a collector author makes by analogy). Values come from `OpticalCycler.GetDynamicAt`, keyed by **component name**, with one elapsed offset per response taken from the optical engine's own `StartTime()`. `config/` and `state/` return the same value for the four scalars — a simulator's configured intent cannot diverge from its operational state. **Three invariants worth not breaking:** (1) the `ifCounters`/`Unavailable` guard lives INSIDE the interfaces branch — hoisted, it asserted the *interface* engine for optical paths, so an optical Get on a device with no HC counters failed with a misleading "interface counters not initialized"; (2) optical absence is `NotFound` on a packet device (permanent) but `Unavailable` on an optical type mid-initialisation (retryable) — `IsOpticalDeviceType` decides, and conflating them tells a client to poll forever for a surface the device cannot have; (3) `ClassifyLeaves` reads no value engine at all, which is what keeps ON_CHANGE rejection cheap and unable to return `Unavailable`. ON_CHANGE on an optical path is rejected `InvalidArgument` with a **leaf-class-branched** message (`isOpticalLeafSelector`) — the counter wording would tell an operator that `osnr` is a counter. `Capabilities` advertises `openconfig-terminal-device` 2026-01-14, `openconfig-platform` 2025-07-15 and `openconfig-platform-transceiver` 2026-03-25 (the last is **not** decoration: `optical-channel/state` reuses its `optical-power-state` grouping for input/output power and laser bias). `post-fec-ber` is **not** served though OpenConfig defines it — Ciena removed it, so a rule keyed on it would never fire against real hardware; `TestOpticalPathManifest` asserts its absence so "completing the model" requires editing a test that explains why. That test also pins served == manifest in both directions, catching an invented or dropped path in CI; it does **not** prove manifest == YANG (the table was traced by hand against the pinned revisions — a ygot check would need them vendored).

**gNMI dial-out (telemetry push, `add-gnmi-dialout`):** `gnmi_dialout_transport.go` (`DialoutTransport` seam + `gnmiReverseTransport` over `github.com/aristanetworks/goarista/gnmireverse`, the Arista `gNMIReverse.Publish(stream SubscribeResponse) → Empty` fire-and-forget flavor; also the shared `parseGnmiPath` / `parseDialoutEncoding` helpers) + `gnmi_dialout_exporter.go` (`GnmiDialoutExporter`: per-device `grpc.ClientConn`+`Publish` stream held in `atomic.Pointer`, own dial→publish reconnect loop with 1s→30s capped backoff, SAMPLE ticker + ON_CHANGE `InterfaceState.AddListener` fan-out, bounded send channel with drop-oldest via `pushOrDrop`) + `gnmi_dialout_manager.go` (`StartGnmiDialoutSubsystem` / shutdown-only `StopGnmiDialout`, `startDeviceGnmiDialoutExporter` captured-pointer-under-RLock attach, `buildDialoutCreds`, `gnmiDialoutAggregates` monotonic per-(collector,flavor) counters, `GET /api/v1/gnmi/dialout/status`). **Dial-out reverses the gRPC role, not the data direction** — the device is the client. Payload generation (`pathResolver`→`encodeUpdates`) and state fan-out are reused verbatim from dial-in, so dial-out/dial-in/SNMP/sFlow agree byte-for-byte at the same instant; only transport + pacing are new. Every dial-out notification carries `Notification.Prefix.Target` = device IP (in-band identity, à la Arista `-target_value`; dial-in responses stay prefix-less). **One ClientConn + one stream per device** (NOT a shared pool — a single Go ClientConn caps at ~100 concurrent HTTP/2 streams); the client dials from inside the device netns with source IP = device IP (reuses the existing veth + FORWARD egress rule). Two-level config: `[seed]` flags (`-gnmi-mode dial-out`, `-gnmi-dialout-*`) for the auto-start batch + a per-device `gnmi_dialout` REST block (`DeviceGnmiDialoutConfig`), enabling a **mixed dial-in/dial-out fleet**. TLS: `tls.enabled=false` → plaintext; else verify against `ca_pem`/system roots (or `insecure_skip_verify` dev toggle), optional `mtls` reuses `sharedTLSCert` as a **client** cert (it cannot verify the collector — hence `ca_pem`). **`ca_pem` is INLINE, never a path**: the block is REST-settable and a path would be an arbitrary-file-read primitive (CodeQL `go/path-injection` — flagged on the syslog twin, missed here only because CodeQL analyses changed code). A path is accepted solely via `-gnmi-dialout-tls-ca`, read once at startup by `loadTLSCAFile`; `tls.ca_file` is now REJECTED with migration guidance rather than ignored. **`certificateBlocksOnly` strips every non-CERTIFICATE block from a bundle at BOTH entry points (CLI load and REST validate), for syslog and dial-out alike** — `AppendCertsFromPEM` returns true as soon as one cert parses and ignores other blocks, so a combined chain+key file would otherwise store the operator's PRIVATE KEY and serve it via `GET /api/v1/devices`, which echoes `gnmi_dialout` unredacted. `ca_pem` is bounded at 64 KiB (`maxCAPEMBytes`), and is parsed at Validate rather than at attach so a bad bundle is a 400 instead of a 201 followed by per-device silence. Drop-on-outage, no buffering; `StopGnmiDialout` is shutdown-only. See `docs/reference/gnmi-dial-out.md`.

**LLDP topology:** `topology.go` (`Topology` — a `SimulatorManager`-owned, mutex-guarded graph of undirected `(deviceIP, ifIndex)` links; the single source of truth for inter-device connectivity) + `lldp_table.go` (the dynamic SNMP provider). Configured via `-topology-config` at startup and `POST` / `GET` / `DELETE /api/v1/topology` at runtime (`topology_api.go`); pruned on `DeleteDevice`. Validation at add time is **syntactic only** (no self-loop, no duplicate, one link per local port — point-to-point); device existence and ifIndex ownership resolve **lazily at SNMP-serve time**, so a link may reference an auto-start device the background goroutine hasn't created yet. The provider serves the Enlinkd-minimal LLDP-MIB subset (`1.0.8802.1.1.2`): `lldpLocalSystemData` + `lldpLocPortTable` + `lldpRemTable`, plus an `ifAlias` (ifXTable .18) link label `to_<peerSysName>_<peerIfDescr>`. It hooks `snmp_handlers.go` `findResponse` (GET) and `findNextOID` (WALK) — the latter adds an `lldpClear` fast-path term (LLDP sorts *before* all static OIDs) and an `overrideLLDP` walk-value rewrite (so the dynamic ifAlias wins over a statically-shipped `.18.N` on GETNEXT/GETBULK). Stitching invariant: `lldpRemChassisId`/`lldpRemPortId` are derived from the *peer's* canonical sources (the `02:42:<ipv4>` chassis MAC and the peer's `ifDescr`), identical to what the peer advertises locally, so Enlinkd matches the two half-links. `lldpRemTable` rows are oper-status-aware (emitted only when both ends are UP; a peer with no state engine is treated as UP; nil-guarded); `ifAlias` reflects configured intent and persists when the port is DOWN. Reads the global `manager` (like gNMI), so no per-device field or device-creation-path change. Walk anchor: a mib-2-rooted walk never reaches `1.0.8802` — point Enlinkd at the LLDP root. Out of scope: capability bitmaps, `lldpStatistics`/`lldpConfiguration`, gNMI/openconfig-lldp.

**DNS service discovery:** `dns_zone.go` (pure, dependency-free zone model — `sanitiseDNSLabel`, deterministic collision disambiguation, `in-addr.arpa` reverse-zone parse/membership, `buildZoneView` producing forward `A` (`<device>` + `ip4.mgmt.<device>`) + reverse `PTR` records + status counters, monotonic `nextSerial`) + `dns_server.go` (`miekg/dns` hidden-primary authoritative server bound in the **default** netns on `-dns-listen` (`:5353`): SOA/NS/A/PTR direct answers, AXFR streaming in 256-record envelopes, IXFR→AXFR fallback, concurrent context-cancellable NOTIFY sender, apex SOA/NS fast path that skips the full rebuild) + `dns_manager.go` (`SimulatorManager` implements the server's `zoneDataProvider` — `DNSDevices`/`ZoneSerial` over the live device map, no per-device DNS state; `StartDnsSubsystem` / shutdown-only `StopDnsSubsystem`; `markDNSDirty` funnelled from every device create/delete; debounce worker coalesces a burst into one serial bump + one NOTIFY round) + `dns_api.go` (`GET /api/v1/dns/status`, `-dns-domain` validation, comma-list flag split). Off by default (`-dns-enable`); the zone content is a derived view over `ListDevices()` (like the LLDP/topology providers). nl6 is the hidden primary; a CoreDNS secondary transfers the zones (`examples/coredns-sidecar/`). Forward `<device-name>.nl6.local` → mgmt IP; reverse PTR → `ip4.mgmt.<device-name>.nl6.local` (round-trips). Names are sanitised `sysName`; duplicates disambiguated by ascending-IP order. **Topology visualization (web console):** `web/topology_logic.js` (pure, DOM-free, node-tested in `topology_logic.test.js`: model building, layouts, structure/state diffing, click-to-flap target resolution, scale guard) + `web/app_topology.js` (sigma.js/graphology glue, poll loop, interaction). **Resource loading:** `resources.go` loads and caches the 389 JSON files at startup. Each device type directory has split JSON files for SNMP, SSH, and REST responses that are merged at load time.

**`resourcesCache` is guarded by `resourcesCacheMu` (nl6#555).** `LoadSpecificResources` runs on the `net/http` handler goroutine via `resolveCreateResources`, so two concurrent `POST /api/v1/devices` naming different device types were a concurrent map write — which the runtime answers with `throw()`, past any `recover()`, killing the whole simulator rather than one request. **The canonical locking rule lives in the `resourcesCache` comment in `types.go`** — which operations the lock covers, why it is not held across the load, and why an `RWMutex` rather than a `sync.Map` or `sm.mu`. Do not restate it here; the two copies had already diverged once. Two points that are not in that comment: **there are TWO write sites**, because a device type shipped as a directory publishes from `loadSpecificResourcesFromDir` while a legacy single-file type publishes from `LoadSpecificResources` itself, and a test suite that writes only directory fixtures leaves the single-file lock pinned by nothing; and a rejection is still **not** cached, deliberately, so a type stays re-triable once the operator fixes the file (the nl6#538 classification is untouched). Pinned under `-race` by `resources_cache_race_test.go`, which covers both layouts plus a mixed row. Without the lock that test reports a data race **deterministically under `-race`** and a `fatal error: concurrent map writes` on most but not all runs without it — the runtime's concurrent-write detection is best-effort, the race detector is not. CI gates on `make test-race` (`.github/workflows/gates.yml:102`), which is what makes the guard observable there.

### Key design decisions

- **sync.Map for OID lookups** — lock-free O(1) access during concurrent SNMP queries
- **Pre-computed next-OID mappings** — efficient SNMP GETNEXT/WALK without scanning
- **Buffer pool** — reduces GC pressure on SNMP request handling
- **Shared SSH/TLS keys** across all devices — avoids per-device key generation overhead
- **Network namespace isolation** (`nl6sim` namespace) — prevents systemd-networkd interference
- **Per-device flow egress** — `setupVethPair` installs a `FORWARD -i veth-sim-host -j ACCEPT` iptables rule so that per-device flow exporters can send UDP out of the ns through the host's routing table (Docker-present hosts default FORWARD to drop). Rule is removed in `NetNamespace.Close`. The simulator image includes `iptables` for this reason. On the downstream flow collector, `rp_filter` may need to be relaxed (`net.ipv4.conf.*.rp_filter=0` or `2`) to accept packets with 10.42.0.0/16 source IPs.

### Device types

29 device types across 9 categories: Core Routers, Edge Routers, Data Center Switches, Campus Switches, Firewalls, Servers, GPU Servers (NVIDIA DGX-A100/H100/HGX-H200), Storage Systems (AWS S3, Pure Storage, NetApp ONTAP, Dell EMC Unity), Optical Transport (Ciena Waveserver 5).

**Optical value engine (`optical_cycler.go`):** `OpticalCycler.GetDynamicAt(component, leaf, t)` is the single dispatcher for every coherent-optical leaf, keyed by **OCH component name** (never `ifIndex`). Same contract as `IfCounterCycler`: pure function of elapsed time, no per-channel goroutine, immutable after publish, single-init panic guard, per-channel jitter over a **sorted** channel slice (seed salt `^0x4F43_0000`). **Two independent dials** — received power `pIn` and accumulated noise `nAse`, with `osnr = pIn − nAse` in dB — because a single power dial makes OSNR perfectly correlated with power and leaves the *attenuation* (low power / normal OSNR) and *ASE* (normal power / low OSNR) quadrants unreachable. Cascade: `osnr → q-value → pre-fec-ber` (`½·erfc`, monotonic — the erfc tail is **shallow** at the 2e-2 SD-FEC threshold, ~3× per 2 dB, so decade-scale assertions there are wrong physics) `→ fec-uncorrectable-blocks`. Off-spine leaves (`output-power`, `target-output-power`, `laser-bias-current`, `chromatic-dispersion`, `polarization-mode-dispersion`, `polarization-dependent-loss`, `frequency`, `operational-mode`, `line-port`) read none of the receive dials — that flatness *is* the fibre-vs-transponder diagnostic. Both dials share a period so their difference collapses exactly to one sinusoid, making the above-threshold integral behind the block counter closed-form, O(1) and monotonic by construction. Types come from the **pinned OpenConfig revision** (terminal-device 2026-01-14 + platform-transceiver 2026-03-25), which governs over Ciena's native model: statistics leaves at `fraction-digits 2`, `pre-fec-ber` at `fraction-digits 18`, `fec-uncorrectable-blocks` a bare `uint64` counter with **no** stats container. **`post-fec-ber` is not served** — OpenConfig defines it but Ciena removed it, so a collector rule keyed on it would never fire against real hardware. `-optical-scenario` / per-device `optical_scenario` selects the health band via `opticalBandFor`; only `failing` crosses the FEC threshold. **Band boundaries are sized against the jitter envelope, not the nominal point:** each dial mean is jittered ±`opticalMeanJitterDB`, so the OSNR mean — their *difference* — spreads over ±2× that, stacked on top of the OSNR sine amplitude (≤ `1.1×(pInAmp+nAseAmp)` in antiphase). The tier contracts (`degraded` never accrues uncorrectable blocks, `failing` always does) must hold for every channel of every seed, so changing any mean, amplitude, or the jitter constant invalidates the arithmetic documented at `opticalBandFor` — `TestOpticalBandContractsHoldAcrossSeeds` sweeps seeds because a single-seed test passes while a fleet-sized share of channels violates the contract. **Capability symmetry with flow:** a non-clean `optical_scenario` on a type with no OCH inventory is rejected **400** (`opticalIncapableRequest`, the inverse mirror of `flowIncapableRequest`), and `opticalScenarioFieldFor` omits the field from `GET /api/v1/devices` for non-optical types rather than reporting a knob that does nothing.

**On-demand optical degradation (`optical_degrade.go`, `optical_api.go`):** `POST /api/v1/devices/{ip}/optical/{component}/degrade` with `input_power_drop_db` / `noise_rise_db` / optional `duration` (24h cap; neither offset = clear). Two knobs, not one severity dial — they select the diagnostic quadrant (attenuation: power down, **OSNR unchanged** — the sag hits `pInAt` AND `nAseAt`, because signal and accumulated ASE traverse the same fibre, so it cancels out of `osnr = pIn − nAse`; ASE: power held, OSNR down). Crossing the FEC threshold therefore requires `noise_rise_db`, which is the discrimination collector rules key on and the reason the engine has two dials. **Degradation is an append-only list of immutable `opticalEpisode`s** (`atomic.Pointer[[]opticalEpisode]` per channel, copy-on-append), NOT an install-and-clear pointer: `fec-uncorrectable-blocks` is the time integral of an above-threshold indicator over `[0,t]`, so clearing a "current sag" would remove already-elapsed degradation from the integral and make the counter **decrease** — a collector reads that as a device reboot. Two load-bearing invariants: a published episode's window is frozen (past segments can never change → monotonic by construction), and `t0` is never in the past (no already-observable value is rewritten; a backdated request clamps forward). The one permitted mutation is truncating an *open* episode's end forward to `now` when a later POST supersedes it. `aboveThresholdSeconds` is therefore **piecewise**: the OSNR mean steps at episode boundaries, so the interval splits there and the same closed-form arcsine applies per segment (cost O(boundaries), not O(t); an undegraded channel takes the original single-segment path). The sag is applied in `pInAt`, `nAseAt` **and `osnrAt`** — `osnrAt` reads the precomputed phasor, so sagging `pInAt` alone would move the input-power leaf while leaving the whole cascade untouched. **No revert timer** (deviation from the story's letter, contract preserved): an episode carries its own end and the engine is a pure function of `t`, so the revert is arithmetic — nothing to schedule, cancel, or leak, unlike the interface-state convention which must put mutated state back.

**gNMI decimal values:** `resolvedUpdate.Value` gained `gnmiDecimal{val, digits}` — a distinct type, not a pre-formatted string, because JSON_IETF needs an RFC 7951 quoted decimal while PROTO needs `double_val`; a Go `string` would silently take the `string_val` branch and corrupt an advertised encoding. At 18 fraction digits `double_val` is lossy (inherent to decimal64 in gNMI's PROTO scalar set); JSON_IETF preserves the digits.

**Per-device-type protocol capability.** Device types are not uniformly capable. `ciena_waveserver5` is a layer-1 coherent optical transport platform: it performs no L3/L4 inspection and therefore **exports no flow records**. Absence has to be *implemented*, not omitted — `GetFlowProfile` (`flow_profiles.go`) falls back to `flowProfileEdgeRouter` for any type absent from `flowProfileMap`, so leaving a type out would silently give it edge-router flow ground truth. The explicit marker is `flowIncapableTypes` + `SupportsFlowExport`, consulted at both device-creation paths; a batch-wide flow seed **skips** incapable devices with a log line (so `-flow-collector` stays usable with `-round-robin`), while a request whose entire resolved type set is incapable is rejected with **400** (`flowIncapableRequest`). Its optical inventory is keyed by OCH **component name** (`OCH-1-1`) in an `optical` resource part, never by `ifIndex`; `validateOpticalInventory` fails the load loudly if that part is missing, malformed, or disagrees with `OpticalProfile.ChannelCount`, because the resource decoder is not strict and would otherwise discard it silently.

**Capability-gating boundary (#364):** GROUND-TRUTH-BEARING surfaces — things a collector validates against (flow byte math, optical values) — get per-type fidelity gating (`flowIncapableTypes`, `opticalIncapableRequest`). TRANSPORT PLUMBING deliberately does not: gNMI dial-out is Arista-flavored `gnmireverse` on a fleet with zero Arista types, because its purpose is letting teams test a dial-out collector at scale against a heterogeneous fleet — gating it by fidelity would gate it to the empty set. The absence of dial-out gating is a decision, not an omission. Completeness of the flow maps is enforced in CI (`TestFlowCapabilityCompleteness`: every repo type in `flowProfileMap` XOR `flowIncapableTypes`); operator-supplied custom resource files fall back to the edge-router flow profile with a once-per-type log line, since the compiled-in maps are unreachable to them.

Each device type has resource files under `resources/<device-type>/` containing JSON for SNMP OID responses, SSH command responses, and REST API responses.

## Source file headers

This repo is a fork of `saichler/l8opensim`. Header policy depends on whether a source file is **forked** (basename exists in `go/simulator/*.go` upstream) or **new** (created in this fork):

- **Forked files** keep upstream's full Apache 2.0 boilerplate header verbatim. Do not replace, trim, or modify it — Apache 2.0 §4(c) requires the original copyright notice be preserved when redistributing.
- **New files** (every file in `go/nl6/` whose basename has no upstream counterpart) get the canonical SPDX-short header, no exceptions:

  ```go
  /*
   * Copyright <YEAR> Ronny Trommer <ronny@no42.org>
   * SPDX-License-Identifier: Apache-2.0
   */
  ```

  - `<YEAR>` = file's creation year. Do not bump it on every edit.
  - Email in angle brackets (`<…>`), not parens — REUSE/SPDX scanner convention.
  - **No `Created by` line.** Authorship lives in `git log`, not in headers — it goes stale and conflates authorship (factual) with copyright (legal).
  - Header sits at the very top of the file, with one blank line between the closing `*/` and the next non-blank line (`//go:build` directive, `package` clause, or a leading comment block).

This overrides the OpenNMS Group form in the global `CLAUDE.md` for this repo only — the override is intentional because this fork is a personal project under no42.org, not OpenNMS Group work.
