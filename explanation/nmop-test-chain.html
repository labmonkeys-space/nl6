nl6 in the NMOP YANG-Push test chain

nl6 is a live YANG-Push publisher for the message broker chain of draft-ietf-nmop-yang-message-broker-integration. It takes the place of the packet capture replay used in the IETF hackathon tests. The publisher is a simulated Huawei NE8000 whose messages follow published captures of a real router.

This page is for readers who know the draft and have not used nl6. The flags and the API are on the YANG-Push reference page.

nl6 is only the publisher. Everything to the right of it is the software under test.

What nl6 changes compared with a capture replay​

The last row is the cost. A replay is the router. nl6 is a model of it, and the next section says how close the model is.

What the simulated router sends​

Each device starts three subscriptions on ietf-interfaces.

IDModeFilter
8periodic, 60 s/ietf-interfaces:interfaces/interface/statistics
9periodic, 60 s/ietf-interfaces:interfaces/interface
10on-change, dampening 5 s/ietf-interfaces:interfaces/interface

The behaviour on the wire follows captures in network-analytics/ietf-network-analytics-document-status.

BehaviourCapture
YANG library, module sets and featuresIETF 123
Subscriptions 8 and 9: subscription-started, push-update leaves and their order, segment sizesIETF 125, yangpush-publisher/huawei-vrp-ip
Subscription 10: subscription-started, the sync push-update, the YANG Patch target and value of a push-change-updateIETF 127, mb-alive-test-result, the router's subscription 11
One message counter per publisher for the UDP-notif message ID and the envelope sequence-number, starting at 1IETF 127 packet capture, all 2446 messages
subscription-started with module-version and yang-library-content-idIETF 125 and IETF 127

nl6 differs from the captures in these points:

  • The subscription IDs are 8, 9 and 10. The IETF 127 router uses 6, 11 and 12 for its interface subscriptions and has no statistics subscription.
  • higher-layer-if and lower-layer-if are not sent.
  • The sync push-update of subscription 10 follows subscription-started at once. The router sends it 5 seconds later.
  • patch-id is a counter per device. The capture holds one change-update and cannot confirm that.
  • Changes inside a dampening period are collected into one update, as RFC 8641 describes. The capture cannot confirm that either.
  • The served YANG library holds only IETF and IANA modules. nl6 adds two features and a few augmented-by rows that the router's library does not list, because the payloads it sends depend on them.
  • Every interface appears in subscription 8. The router sent statistics for a subset.
  • The values are simulated. Interface names, counters, addresses and descriptions come from the nl6 device profile.

The limitations file has the full list.

Run the chain​

yang-push-clickhouse-e2e holds the whole chain as one Compose stack. Its README has the steps. It needs a Linux Docker engine, starts three devices by default and ends with a count of the messages at four points in the chain.

The stack pins the nl6 release v0.40.2. That release has an older subscription 10 and one message counter per subscription. Set NL6_IMAGE to a build of nl6 main to get the behaviour on this page.

What a run shows today​

Result of 18 November 2026 with a build of nl6 that has the subscription 10 described above, three devices, about three minutes of traffic:

Point in the chainMessages
Sent by nl632

Produced to Kafka32
Stored by the consumer32

No message is lost. The 14 invalid messages fail strict validation at the consumer for two reasons, and the captured router sends both shapes too.

  1. An identity module is not in the registered schema. Interface entries carry type values such as iana-if-type:ethernetCsmacd. subscription-started names only ietf-interfaces in module-version. iana-if-type is not reachable from it through imports, augments, deviations or features, which is the dependency rule of section 4.3 of revision 13 of the draft. The consumer validates by Schema ID, as section 4.7 describes, and cannot resolve the identity.
  2. The YANG Patch value of an on-change update is not rooted at a top-level node. The router writes the value as {"interface":[...]} for the target /ietf-interfaces:interfaces/interface[name=...]. libyang rejects it with Node "interface" not found.

The first finding was measured with a changed device. When the device names iana-if-type in module-version, the consumer validates every interface push-update. A receiver with strict validation still drops them, because the device lists the module as import-only and the receiver keeps that marking. Receiver and consumer then validate against different contexts built from the same library.

The receiver in this chain runs with anydata_strict_validation off. That is why it forwards all 32 messages.

What nl6 does not cover​

  • Only ietf-interfaces. The IETF 127 capture also has hardware, LLDP, alarm and Huawei native subscriptions.
  • Three fixed subscriptions per device. A subscription cannot be configured over NETCONF, and the dialect serves only get, get-schema, close-session and kill-session.
  • One vendor. Only huawei_ne8000 streams YANG-Push.
  • JSON over UDP-notif only.
  • No loss ratio per device. The chain compares totals. Reconciliation per device needs YANG-Push as a load-test protocol, which nl6 does not have yet.
